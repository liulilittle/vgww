## 1. P1 逐项

### P1-1 租约文件字段类型错误 → 数据面启动失败（契约破坏）

**症状**：租约 JSON 语法合法但某条目的 `mac`/`ip`/`hostname`/`iaid` 类型不对时，
`LoadLeases` 抛 `nlohmann::json::type_error`，逃出 proto 层；`StartAll` 的 catch 把它
变成 `dataplane start failed: ...`，主模式 DHCP 用户**整机不启动**（而不是文档承诺的
「降级为空租约表继续启动」）。

**证据**
- 解析的 try/catch 只包 `nlohmann::json::parse(raw)`：`dhcp.cpp:1310-1324`，`dhcp6.cpp:1093-1101`。
- 遍历条目的取值在 try 之外：`dhcp.cpp:1375`（`item.value("mac","")`）、`:1378`（`ip`）、
  `:1452`（`hostname`）；`dhcp6.cpp:1162`（`duid`）、`:1166`（`iaid`）、`:1168`（`ip`）、`:1222`（`hostname`）。
- `value()` 命中 key 后直接 `it->template get<ValueType>()`：`json.hpp:21534-21538`；
  字符串取值在非 string 时 `JSON_THROW(type_error::create(302, "type must be string..."))`：
  `json.hpp:4723-4725`；数字取值同型（`json.hpp:4702-4706`）。
- 逃逸路径：`StartAll` 声明为 `bool StartAll(std::string& error) try {`（`dataplane.cpp:805`），
  尾随 catch 全部 `return false`（`dataplane.cpp:1191-1228`）；`main.cpp:606 if (!dataplane.Start(error))` 走启动失败分支。

**根因链**：损坏/手改租约文件 → `parsed` 成功 → `for (item : parsed)` 取字段 →
类型不匹配抛 `type_error.302` → 冒出 `LoadLeases`（`nothrow` 语义只覆盖了 `parse`）→
`StartAll` catch → `Start` 返回 false → 进程进入「数据面未启动」状态。

**可达性**：需要一个「语法合法、字段类型非法」的租约文件（磁盘损坏、编辑器改坏、
旧/新 schema 混写、外部工具写回）。不需要网络访问。正常 Dump 出来的文件不会触发
（`dhcp.cpp:1136-1140` 用 nlohmann 构造，类型固定）。

**为什么是 P1 而不是 P0**：异常被 `StartAll` 的 catch 兜住，不会 terminate；
但「损坏文件必须降级」是被测试固化的契约（`test_dataplane_lifecycle.cpp:1083` 注释
"a corrupt lease file must degrade to an empty table without crashing"，
用例用截断 JSON `:1110`，恰好只覆盖了 parse 阶段，没覆盖条目类型错误），因此定性为功能损坏。

**建议最小方案**：把「遍历条目」整体包进 `try { ... } catch (...) { return corrupt(); }`
（与 `parse` 同级），或在取每个字段前用 `is_string()/is_number_unsigned()` 判定并 `++dropped`；
后者与既有「逐条丢弃并计数」语义更一致（`DroppedLeaseCount`）。
必须补一条红测：`{"version":1,"leases":[{"mac":123,"ip":"192.168.0.100"}]}`
→ 期望 `kRestored`（或 `kCorrupt`）+ 不抛异常；改坏判定后必须转红。

## 2. P2 逐项（防御/契约/性能）

### P2-2 `ParseDhcpFrame` 不复位 `out.hostname`
`out.msg_type/requested_ip/server_id` 每次清零（`dhcp.cpp:111-113`），`hostname` 只在
code==12 时 `assign`（`:159-162`）。DHCPv6 兄弟上来就 `out = Dhcp6View{}`（`dhcp6.cpp:112`）。
当前唯一生产调用点是每帧新建局部 `proto::DhcpView dhcp;`（`dataplane.cpp:2688`），**today 不可达**；
但契约不对称、且 `Acquire` 的「空名保留旧名」语义（`dhcp.cpp:361-363`）会把脏名字固化进租约。
建议：函数入口 `out = DhcpView{}`（与 v6 对齐）。

### P2-3 DHCP 精确长度校验 vs 分类器双向认领
分类器把 `67/68` 任一端都判成 `kDhcpV4`（`classifier.cpp:192-196`）；
`ParseDhcpFrame` 只接受 `dport==67` 且 `udp_len_field == len-14-ihl`（`dhcp.cpp:82-91`），
并 `reject()` 累加 `g_parse_rejected`（`:36`、`:46-49`）。
生产调用点 `dataplane.cpp:2689-2691` 把失败一律 `++stats->rx_dropped`。
后果：网段内另一台 DHCP 服务器的 OFFER/ACK（68→67 之外的 67→68）每帧都被计入
「畸形帧」和 rx_dropped，掩盖真实畸形率。建议：`dport==68`（服务器→客户端方向）在
解析器内**静默忽略**（不计 reject），或让分类器只认 dst∈{67}。

### P2-4 不支持 DHCP relay
`ParseDhcpFrame` 读取了 `xid[4..7]`、`ciaddr` 未读、`chaddr[28..33]`、`giaddr` 完全未读
（`dhcp.cpp:99-122` 的读取集合）；`BuildDhcpReplyFrame` 固定 IP 目的 255.255.255.255
（`dhcp.cpp:255-257`）。因此 `giaddr≠0` 的中继请求会得到「直接广播给客户端」的回复，
中继代理收不到（RFC 2131 §4.1：giaddr 非零时必须回 giaddr:67）。
当前定位是「LAN 侧虚拟网关」，可接受，但属于未声明的能力边界；建议在头注释显式写死
「giaddr≠0 不支持」，并在解析器里拒绝 `dhcp[3] != 0 || giaddr != 0`，避免中继场景静默错答。

### P2-5 DHCPv6 运行时绑定 hostname 丢失
runtime 分支：`if (!hostname.empty()) { lease.hostname = reported_name; }`（`dhcp6.cpp:568-570`），
没有 `else`；config 分支有 `else { lease.hostname = binding.hostname; }`（`:581-583`）。
`HandleFrame` 传的是 `std::string()`（`:1634`、`:1653`），所以运行时绑定的名字**永远是空**，
`Leases()`（`:1277`）也就永远显示空名（`StaticBindings()` 里是对的）。
建议：runtime 分支补 `else { lease.hostname = runtime->second.hostname; }`。

### P2-6 ICMP 回包上限未扣 VLAN 头
`kMaxEchoReplyFrameBytes = 1514`（`icmp.h:35`，注释称"matching Dataplane::AppendDown's send cap"），
但 `AppendDown` 的实际上限是 `config.vlan.enabled() ? 1514-4 : 1514`（`dataplane.cpp:3751-3754`），
驱动侧 `MAX_ETHER_FRAME 1514`（`Common.h:96`）。
满长（1500B IP）echo 请求在 VLAN 模式下生成 1514B 回复 → `AppendDown` 丢弃并 `++rx_dropped`。
建议：栈缓冲尺寸改为 `1514 - net::kVlanTagLen`，或让 `AppendDown` 的返回可观测（当前是 void）。

### P2-7 DHCPv6 池尺寸溢出
`const uint64_t pool_size = pool_end_index_ - pool_start_index_ + 1;`（`dhcp6.cpp:643-644`）：
当 `pool_start_index_==0 && pool_end_index_==UINT64_MAX` 时结果回绕为 0，
`for (offset = 0; offset < 0; ...)` 一次都不跑 → 池被当成空池（`NoAddrsAvail`）。
候选式 `pool_start_index_ + ((next_index_ - pool_start_index_ + offset) % pool_size)`（`:663-666`）
在 `pool_size > 2^63` 时同样可能回绕到区间外。
配置侧只校验「池在前缀内 + end≥start」（`config.cpp:1315-1323`，prefix_len≤64 `:1440-1442`），
所以「IID 覆盖半个以上空间」是合法配置。可达性极低（需 /64 前缀 + 巨池 + 边界值），
但属于可构造的错误行为；建议 `if (pool_size == 0) return {};` 并 clamp 索引到 `[start,end]`。

## 3. 「看起来可疑但实际正确」——证明不该改

1. **DHCPv4 option 循环无死循环**：`pos += 2 + opt_len`（`dhcp.cpp:166`），`opt_len==0` 也推进 2；
   `pos+2+opt_len > dhcp_len` 先 break（`:139-141`）；`pos` 为 `size_t`，`opt_len` ≤255，
   无溢出。PAD 分支单字节推进（`:131-134`）。→ 终止性完整，**不该改**。
2. **DHCPv6 严格 option 遍历**：`pos + olen > payload_len → fail`（`dhcp6.cpp:170-172`），
   结尾 `pos != payload_len → fail`（`:229-231`）拒绝尾随垃圾；IA_NA 内层同样两段校验
   （`:196-215`）。已由 `test_dhcp6.cpp:1659-1690` 固化（含「隐藏第二个 ClientId」「短 1 字节」
   「长 1 字节」三个决定性样本）。→ **不该放宽**。
3. **`ParseIcmpEcho` 的 total_len 兜底分支**（`icmp.cpp:36-40`）：`total_len` 越界时回落到
   `ip_len - header_len - 8`，而前一行已保证 `ip_len ≥ header_len+8`，无下溢；
   `test_icmp.cpp:210-254` 覆盖四类畸形。→ **不该改**。
4. **`IcmpSegmentLength` 与 relay 的无符号减法**：`out_len = total_len - header_len`（`icmp.cpp:61`）
   前已判 `total_len ≥ header_len+8`；`RelayEchoReplyToClient` 的
   `segment_len - kIcmpHeaderLen`（`:232`）同样有下界保证。→ **无下溢**。
5. **`BuildEchoReplyV6Frame` 双边界**（`ndp.cpp:279-291`）：上界 `40+payload_len ≤ request_len`
   （batch34v OOB 读）与下界 `payload_len ≥ 4`（batch125 写越界）缺一不可；删任一条都会回归。
   → **不该合并/简化**。
6. **`UdpSegmentLengthV4/V6` 的 ip_len 回落**（`udp.h:72-77`、`:99-107`）：
   「声明的比抓到的大」时取抓到的长度，保证后续 `memcpy` 不越过真实缓冲区；jumbogram(0) 明确拒绝。
   → **正确**。
7. **`ParseArpFrame` 的 oper 白名单**（`arp.cpp:38-40`）：注释说明「其它 operand 不得折叠成
   kRequest，否则乱码报文会拿到网关 IP 的 gratuitous 回复」，且 `len < kArpFrameLen` 先挡住
   28 字节 body 读（`:16-18`）。→ **不该改**。
8. **`BuildDhcpReplyFrame` 的 TLV 长度截断**：`len = min(value.size(), kMaxHostnameBytes)`
   同时截断写入字节数（`dhcp.cpp:189-194`），不会出现「长度字段与实体不符」的流错位，
   `test_dhcp.cpp:2319` 固化。→ **不该改**。
9. **DHCPv4 `pool_size` 的 uint32 运算**（`dhcp.cpp:402`、`:484-486`）：
   要 `end-start+1` 溢出需 `start==0`，而 `:393` 已拒绝 `0==start`；`next_dynamic_-start+offset`
   的回绕被 `% pool_size` 吸收，候选仍落在池内（池 ≤ LAN 主机数）。→ **构造上不可达**。
10. **`ApplyHostname` 的 UTF-8 双路径**：线上路径 `SanitizeUtf8`（`dhcp.cpp:341`），
    控制面 `IsValidUtf8` 拒绝（`:729`）；`DumpLeases` 的 `row.dump()` 因此 total
    （`test_dhcp.cpp:2429-2455` 出红）。→ **不该统一成一种**。

## 5. 自我证伪（我的结论哪里可能错）

1. **P1-1 可能被高估**：如果产品对「租约文件损坏」的既定策略其实是「拒绝启动并告警」，
   那这是设计而非缺陷。反证点：`LoadOutcome::kCorrupt` 的注释明确写「the file IS preserved」
   且 v4/v6 都有「corrupt → 降级空表」的用例（`test_dhcp.cpp:687-718`），而 `StartAll`
   的日志文案把 kCorrupt 描述成 "LEASE FILE UNREADABLE - mappings lost"
   （`dataplane.cpp:1061-1062`）——说明作者期望的是「继续跑」。→ 我的判断成立，
   但**若**维护者认定为「应拒绝启动」，则应删掉 P1、并把契约写进注释与测试。
2. **P2-2 可能被反驳**：「调用方每帧新建 view」是硬事实（`dataplane.cpp:2688`），
   所以今天不可达，只有契约风险。若审计乙认为「不可达即不该报」，我接受降级为 P3/备忘，
   但 v6 兄弟的 `out = Dhcp6View{}` 证明作者本意是「入口清零」。
3. **P2-3 可能错**：如果分类器实际上从不让 67→68 的帧进入 `kDhcpV4`
   （例如驱动方向过滤），则无污染。核验方式：`dsp::ClassifyFrame` 对 dst=68 的 UDP
   确实置 `kDhcpV4`（`classifier.cpp:192-196` 无方向判断），且 `DispatchFrame`
   对 inbound 帧不区分方向 → 我的结论成立。**但**若交换机侧不回传服务器→客户端帧，
   则只是理论指标噪声，实际频率取决于网络拓扑。
4. **P2-6 的量级可能夸大**：只有「1500B 载荷的 echo 请求 + 启用 VLAN」同时满足才丢包；
   普通 ping（32B）不受影响。若维护者认为满长 ping 不是必须支持的场景，可降为 P3。
5. **P2-7 可能不可达**：`pool_start_index_==0` 需要 `pool_start == prefix::0`，
   而 UI/配置是否允许「前缀本身」作为池起点尚未验证（W5）；若不合法，则溢出分支不可达，
   应降级为文档项。
