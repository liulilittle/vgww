## 分歧 1 —— 乙审 P1-1「租约表无条目数上限 → 远程内存增长 + RX 线程停滞」

### ① 池上限的实际可达规模（硬证）

租约表的**实际上界**不是「无界」，而是 `pool_size + kMaxStaticBindings`：每个 lease 必须先拿到
一个空闲池地址才能插入。

- 动态插入点：`dhcp6.cpp:686`（`Lease& lease = leases_[key];`），位于 `for (offset < pool_size)`
  循环体内，且 `taken`（`:669`）与 `ReservedByStatic`（`:683`）都不成立才落到这里
  → 每个 lease 占一个不同 IID。
- 请求地址分支：`:627` 同样在 `usable` 判定（`:616-625`）通过后插入。
- 两个静态分支：`:564`、`:575` 由 `runtime_bindings_`/`config_.ipv6.dhcpv6.static_bindings` 驱动，
  均被 `kMaxStaticBindings6 = 1024`（`limits.h:34`）与 `config.cpp:786/1478/2641/2768` 卡住。
- v4 同型：`dhcp.cpp:507` 在 `taken/reserved/gateway/lan/bcast` 全不成立后插入（`:501-506`）。

| 协议 | pool_size 上界 | 依据 |
|------|----------------|------|
| DHCPv4 | ~2^31（/1 掩码） | `config.cpp:1198-1204` 只要求池在 LAN 内且 end≥start；掩码须连续 1（`:1181-1185`），故 LAN 可达 2^31 主机；`:1206-1213` 只禁池含网关，`:1222-1232` 只禁**两端**等于网络/广播地址 |
| DHCPv6 | ~2^64-2 | `config.cpp:1315-1323` 只校验「池在前缀内 + end≥start」；`prefix_len ≤ 64`（`config.cpp:105/1441`），IID 空间 64 位 → `::1`（含）到 `::ffff:ffff:ffff:ffff`（含）合法 |

默认配置：`ResolvePool()` 派生 `prefix::1000-::1FFF`（`dhcp6.cpp:496-503`）= 4096 条。
**默认 4096 完全无害；只有运维把池配成天文数字时才成为真风险。** 池不是攻击者可控
（攻击者改不了配置），因此「远程」措辞不准确——是「链路上任一台主机」在「巨型池配置」下的 DoS。

### ② RX 线程持 mutex_ 时长（数量级估算，W5）

`Acquire` 全程持锁（`dhcp6.cpp:545`；v4 `dhcp.cpp:329`），且 DHCP 解析/应答**在 RX 线程上执行**：
`dataplane.cpp:2137 DispatchFrame(ib, down, up)` 位于 `RxTxLoop`（`:2092`）的读包内层循环，
DHCP 分支在 `:2689-2787` 直接调用 `Acquire`/`HandleFrame`。

单帧代价 = 建 `occupied` 集合 O(leases)（`dhcp6.cpp:654-661`）+ 池走查 O(pool_size)×O(bindings)。

- N=4096（默认）：≈ 0.12ms → 无感。
- N=100,000：≈ 3ms/帧持锁。100 帧/s 即 30% 时间卡锁，同刻其它 DHCP 客户端与
  `Sweep`（`:777-798`，O(N) 持锁，worker0 每 5s 一次 `dataplane.cpp:2977-2982`）全部排队。
- N=1,000,000：≈ 30ms/帧 → RX 线程实质停摆。

累积代价：堆到 N 条需 N 个严格合法的帧，总代价 O(N²)（到 100k 需 ~3e9 次哈希操作）。
这是**需持续投入的 LAN 侧资源耗尽**，不是一帧打崩。

### ③ 结论：新增显式守卫，不要靠池尺寸

池尺寸不是代码不变量（运维配置，上界宽到 2^64），而本库对**所有**「按不可信键增长的表」
都设了硬上限：`kMaxNeighbors`（`limits.h:45`）、`kMaxStaticBindings/6`、
`kMaxRateEntries`（`dhcp6.h:356`、`dhcp.h:289`）。唯独 `leases_` 没有，是**同型纪律漏项**
（`dhcp.h:126-129` 注释还写着 "Bounded map (drop-all when oversized), same cheap discipline as probes"）。

建议最小方案：
1. `Acquire` 所有插入点前加容量检查：`leases_.size() >= kMaxDynamicLeases && !leases_.count(key)`
   → 返回 0 / 全零地址（复用 `pool_exhausted_` 可观测通道）。
2. `config.cpp` ValidateConfig 对 `pool_size` 设上限（如 ≤ 65535），巨型池在启动期即被拒绝。
3. 红测：N+1 个 DUID 的 SOLICIT → 断言 `LeaseCount() <= kMaxDynamicLeases`；改坏检查须转红。

## 分歧 2 —— 乙审 P1-2「`ReservedByStatic` 每候选两次线性扫，与 O(leases+pool) 注释矛盾」

### 表态：**同意乙审，且明确承认「漏报」**

第一轮我读过 `dhcp6.cpp:524-538`、`:645-653`、`:682-684` 三处，**但没有把三者串起来判定为缺陷**。
这是漏报，不是「判定不需要修」。

硬证：
- `dhcp6.cpp:682-684`：`if (0 == index || ~0ULL == index || taken || ReservedByStatic(duid, candidate))`
- `dhcp6.cpp:524-538`：函数体是 config 一次线性扫 + runtime 一次线性扫，均无索引。
- `dhcp6.cpp:645-653` 注释 "A host-set keeps this O(leases + pool_size)" **只对 `occupied` 成立**，
  对 `ReservedByStatic` 不成立——注释与实现不符。
- v4 姐妹实现已做对：`dhcp.cpp:407-418` 预构 `reserved_hosts`，循环 `:501` 用 O(1) `count()`。
  v6 属同型未扫尾（C6 单源违反）。

分级：默认池 4096 + 0~1 绑定可忽略；**池接近满（走查遍历 N 候选）× 1024 绑定
→ 4096×2048 ≈ 8.4M 次 16B 比较 ≈ 20-40ms，全程持 `mutex_`（`dhcp6.cpp:545`）、落在 RX 线程**
→ P2 为主，「大池+接近满+多绑定」组合下可升 P1。

建议与乙审一致：`Acquire` 开头把 config+runtime 绑定 IP 预构为 `unordered_set`，循环内 O(1)；
同步修正 `:645-653` 注释。红测：填满 1024 地址池 + 1024 绑定，用探针计数断言
`ReservedByStatic` 调用次数 ≤ candidates 而非 × bindings。

## 分歧 3 —— 乙审 P2-7 的 dump 半边（`row.dump()` 抛 316 打死控制线程）

### 表态：**同意主代理反证——构造不可达；乙审该半条不成立**

逐路复核「非法 UTF-8 能否进入 `leases_`」：

1. **线上路径**（唯一由不可信对端驱动的入口）
   - v4：`Acquire` 入口 `const std::string reported_name = core::SanitizeUtf8(hostname);`（`dhcp.cpp:341`），
     之后 `lease.hostname` 的写入（`:362`、`:373`、`:385`、`:462`、`:511`）全部写 `reported_name`，
     **无一处写原始 `hostname`**。
   - v6：`dhcp6.cpp:552` 同样先净化；写入点 `:569`、`:580`、`:631`、`:690` 均为 `reported_name`；
     另 `:582` 写 `binding.hostname`（来自 config/runtime，见下）。
   - `SanitizeUtf8` 幂等且输出必为合法 UTF-8（`text.h:96-120`）。
2. **load 路径**：`item.value("hostname", "")`（`dhcp.cpp:1452` / `dhcp6.cpp:1222`）源自
   `nlohmann::json::parse(raw)`（`dhcp.cpp:1314` / `dhcp6.cpp:1095`）；3.11.3 lexer 在
   strict 模式（默认 `json.hpp:9251 const bool strict = true`）逐字节校验
   `next_byte_in_range`（`json.hpp:8119/8129/8153/8163/8173/8185/8195`），非法即 `parse_error`
   → `catch (...) { return corrupt(); }`（`dhcp.cpp:1321-1324`）。孤代理项 `\uD800` 同样被拒
   （`json.hpp:7732-7746`）。
3. **config 路径**：`binding.hostname = h->get<std::string>()`（`config.cpp:537/793`）来自
   `json::parse`（`config.cpp:1776`）→ 合法。
4. **控制面（Web）路径**：`JsonGetString` 手写扫描器确实不校验原始字节（`web_api.cpp:171-300`），
   但到达 store 前被两道闸拦下：
   - `ReplaceBinding`：`if (!hostname.empty() && !core::IsValidUtf8(hostname)) return false;`
     （`dhcp.cpp:729-731`；v6 同型 `dhcp6.cpp:1336-1338`）。
   - `web_api.cpp:3737-3744`：`SetDhcp6Binding` 失败即 400 返回，**在 `PersistDhcpBindingV6`
     （`:3745`）之前**。
5. **`DumpLeases` 自身**：`row` 由 nlohmann 构造、字段类型固定（`dhcp.cpp:1136-1140` /
   `dhcp6.cpp:942-947`），316 只可能由字符串内容触发，而内容已由 1~4 闭合。

→ **316 分支当前不可达**，乙审该半条应撤销。建议仅加 `try { ... } catch (...) { ++persist_failures_; return false; }`
作廉价纵深，不作为现存 bug。

## 分歧 4 —— 分级统一：load 端 `item.value()` 类型异常

### 最终表态：**接受主代理的 P2 定级（我的「整机不启动」措辞被推翻），但保留两条实质内容**

#### 我接受的部分（主代理硬证，我已独立复核）

- `main.cpp:606` → `ClassifyDriverFault` 只对 AccessDenied/DriverMissing 重试
  （`error_class.cpp:9-24` 只认 4 个固定子串），其余 `recovered == false`
  → `dataplane_failed = true` + stderr "continuing in degraded mode"（`main.cpp:665-678`）。
- headless 打印 "VGWW running in DEGRADED mode (dataplane down), press Ctrl+C to stop."（`main.cpp:1173-1176`）。
- `main.cpp:1203 return 0` —— **进程不退出**。
- UI 路径把错误文本交给 `ui_flags.dataplane_error = dataplane_error_text`（`main.cpp:1052`），
  而 `ui/app.cpp:251-265 LocalizeDataplaneError` 对 `DriverFault::Other` 返回
  `Str::DataplaneErrorGeneric` → **操作员看不到「租约文件字段类型错」**。

⇒ 我原先写「主模式 DHCP 用户**整机不启动**」是**措辞错误**，主代理的推翻成立，我撤回该表述。

#### 我保留的第一条：主要风险不止「可诊断性」，而是**同类损坏处置不一致**

同一个文件损坏类别在代码里有两条完全不同的处置：

| 损坏形态 | 处置 | 结果 | 证据 |
|----------|------|------|------|
| JSON 语法错 / 超版本 schema | `corrupt()` | `SetAsideFile(.corrupt)` + `lease_file_corrupt_` + **降级空表继续启动** | `dhcp.cpp:1310-1324`（parse catch）、`dhcp.cpp:1351-1361`（schema）、`dhcp.cpp:1188-1205`（corrupt 本体）、`test_dhcp.cpp:687-718`（固化） |
| 语法合法但字段类型错（`{"mac":123}`） | 异常逃出 `LoadLeases` | 无隔离、无计数、**数据面不启动** | `dhcp.cpp:1375/1378/1452` 在 try 之外（try 只到 `:1339-1343`，`parsed_ok:` 后 `:1346-1460` 无 catch）；`json.hpp:21543`（item 非对象 → 306）、`json.hpp:4723-4725`（非字符串 → 302） |

且失败后 `dhcp_.reset()`（`dataplane.cpp:1202`）→ `DumpLeases` 永不执行、`corrupt()` 永不调用
→ 坏文件原地保留 → **每次重启复现同一失败**，只能手工改文件或删文件。
这与 batch82/batch120 建立的「损坏必须留证据并隔离」契约（`dhcp.cpp:1146-1153`）直接冲突。

**所以：定级可以接受 P2，但「把遍历包进异常边界 → corrupt()」的修复必须做**，
否则这条不一致会长期以「每次重启失败 + 错误文本被 UI 泛化」的形式消耗运维时间。
修复后 P2 的可诊断性问题也随之消失（会变成 `kCorrupt` → 状态面板可见的
`leases_corrupt`，`web_api.cpp` 已有该字段）。

#### 我保留的第二条：这条路径**不是**「正确拒绝启动」

我不同意「拒绝启动是正确行为、缺陷只在错误文案」的框架——因为代码库自己为
「截断 JSON」选择了降级+留证，为「字段类型错」选择了拒绝启动，两者是同一个信任边界上的
两种策略。若确认要「一律拒绝启动」，则应删掉 `corrupt()` 的降级语义并改写
`LoadOutcome::kCorrupt` 的文档与 `test_dhcp.cpp:687-718`；但那是更大的行为变更，不建议。

#### 修复（与定级无关，方案不变）

```cpp
// dhcp.cpp 约 :1362 起（v6 同型 dhcp6.cpp:1160 起）
try {
    for (const auto& item : parsed) { /* 现有整套过滤逻辑保持不变 */ }
} catch (...) {
    return corrupt();   // 隔离 + 计数，符合 batch82/120 契约
}
```
或逐字段防御（与「逐条丢弃计数」语义更契合）：
```cpp
const auto mac_node = item.find("mac");
if (mac_node == item.end() || !mac_node->is_string()) { ++dropped; continue; }
```
红测：`{"version":1,"leases":[{"mac":123,"ip":"192.168.0.100"}]}` 与
`{"version":1,"leases":["not-an-object"]}` → 断言「不抛异常 + (kCorrupt 或 kRestored&dropped>0)」；
把修复改坏必须转红。
