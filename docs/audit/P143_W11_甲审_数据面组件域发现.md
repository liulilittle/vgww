## A. [撤回/误报] tcp_relay.cpp - Socket→Flow 重试状态机(原判 P1 并发死角,乙审反证成立,撤回)

### 原判(已撤回)
原稿将 `retry_pending_` 单 bool 状态机判为 P1:在 kInFlight 同步拒绝与 kOk/kWouldBlock 完成交错时,同一 `up_buf_` 块可能被重复发送或丢失。

### 乙审反证(正确)
1. **kInFlight 实际不可达**:kInFlight 返回条件是 flow 写队列满(`write_queue_.size() >= kWriteQueueCap`,mimt.cpp:77-79)。而 TcpRelay 的 1:1 泵纪律(tcp_relay.h:16-23 + 实现:每次 WriteToFlow 发起后 socket 读不重挂,直到该写完成)保证同一 relay 至多 1 个 chunk 在途 → 队列不可能被本 relay 单独填满至 16。kInFlight 在正常使用下不触达(防御路径)。
2. **kWouldBlock 完成时队列必空**:DispatchWrite 遇 sink 失败会**清空整个写队列+mimt.cpp:196-214 → 无"先前 kOk 入队写"可遗留**为后续 completion;此后 retry_pending_=true,无并发残留写会再来完成。
3. **MimtFlow::AsyncWrite 入队深拷贝**(mimt.cpp:84 `p.data.assign(buf, buf+len)`):被重发的旧字节与 enqueued 副本**完全独立**,up_buf_ 复用不产生数据扰乱。
4. **串行回调 + 单点守卫**:完成与 timer 均在 owner worker 线程串行派发;`retry_pending_` 只有 kOk 分支(tcp_relay.cpp:121)与 timer(tcp_relay.cpp:150)两处清位,均先查再清,clear-only-once。kOk 分支(tcp_relay.cpp:120-122)在 retry_pending_=true 时重发,否则重挂读泵:timer 与 kOk 两者至多一个重发,不会双发。
5. **读永不双挂**:read 只在 PumpSocketToFlow(由 kOk-then-Pump 或 retry 完成后的 kOk→Pump 路径)发起,而发起前 retry_pending_ 必为 false;kWouldBlock/timer 期间读保持暂停 → up_buf_ 不被覆盖。

### 结论
单线程模型(全回调在 owner worker)下状态机**正确**。与测试 TestSinkWindowFullHoldsAndRetries(test_tcp_relay.cpp:411-457)语义一致。**这是误报,已撤回**;对乙审反证致谢。教训:评估"并发死角"时必须先验证"触发前提可达性"——此处 1:1 泵纪律使 kInFlight 前提不可达,原稿仅凭代码形态判激进。

## B. [P2] rate_limiter.cpp - 极小速率下 MakeCapacity 精度丢帧

### 证据
- rate_limiter.cpp:66-70 `MakeCapacity = max(burst_seconds*rate_bps, min_capacity_bytes)`。
- 默认 min_capacity_bytes=1500、burst_seconds=1.0。rate 若配置为 1 kb/s → reserve 125 B/s → capacity=1500,任何 ≥1500B 的帧直接拒绝(需 12s 攒满)→ 合理。
- 但 index 为 `uint32_t kbps`,RateLimitRule 无下限校验:admin 可填 1 kbps 且流量超 MTU 时长包全拒 —— **已文档化**行为("min_capacity 兜底"),非 BUG。

### 根因
- 真正的隐患在 `double` 累计精度:elapsed 以 steady_clock 高精度减,速率极小(如 1 kb/s)时每次 refill 增量 = elapsed_s*125,B,大帧一次花的 token 可超 capacity 数值精度 → 长帧严格限速下 capacity 的 min_capacity_bytes 只是让短帧可爆,长帧(>1500)在 1kbps 下被掐断而非排队。语义正确(限速本来就是 drop-not-grow),**非 BUG,但文档宜注明"最小速率=单帧 MTU/份额"**。

### 结论
防御性文档/注释项 P2(无数据损坏)。不修也不构成正确性缺陷。**证明不改可接受**。

## C. [P1→降级] bridge.cpp - kControlAndFlood 泛洪的地址学习竞争(乙审 A 项交叉确认)

### 证据
- bridge.cpp:186-222 `LearnAndDecide`:先 `table.Learn(src, port)` 再 `table.Lookup(dst)`,同一把 `table_mutex` 下完成。
- bridge.cpp:206-214 try/catch:分配失败(表满时 entries_[mac] 扩容)返回 kDrop —— **帧直接丢**,含未解析的目的地。

### 根因
表满时的 `Learn` 需要 O(1) 容量淘汰(bridge.cpp:40-55),append 进 unordered_map 需要分配;`std::unordered_map::operator[]` 在**已存在 key**时**不重哈希**:rehash 仅发生在插入新 key 导致 bucket 数增长。故"已学 MAC 刷新端口"路径零分配,不抛;仅"新 MAC 入表"路径可能分配失败 → 被 try/catch 降为 kDrop。此路径是**预期的**容量淘汰,不是缺陷。

### 可达性
新设备接入时若恰好表满且分配失败 → 该卡首个待转发帧被 drop(TCP 会重传;UDP 丢)。概率极低(表满+bad_alloc 同时),次生影响只损一帧。**降为 P2 防御项**(可选:失败时降级执行一次"不学习、只泛洪",保转发不断)。测试 test_bridge 未注入表满+分配失败组合。

## D. [P2] neighbors.cpp - 极端情况下 Explore 的重建竞争

### 证据
- neighbors.cpp:45-58 `Tick`:先 `has_updates = !pending_.empty()`,无更新且未超时则跳过重建。
- neighbors.cpp:134 `std::atomic_store(&current_, ...)`:发布快照。
- neighbors.cpp:126-131 重建后 `oldest_` 取当前 `fresh` 快照内最小。

### 根因/死角
`oldest_` 只反映**已发布快照**的最早 last_seen。若 pending 里积累了新 IP(Learn 不更新 oldest_) ,且在两次 Tick 之间所有旧条目老化,但**pending 为空**时:no update + frontier oldest 未超时 → 跳过 → 正常。真正死角是 pending 满 50000 且 Tick 重建后 `oldest_` 更新为新快照,而旧条目全数老化的同时 pending 空 —— 但已重建,无遗漏。

### 结论
未发现真竞态:oldest_ 的读写均为控制线程;RX 线程只看 pending 写。`std::atomic_load(&current_)`(neighbors.cpp:73)与 `std::atomic_store` 构成 RCU;快照不可变不释放前被读 —— **证明不该改**。

## K. 验证闭合项(证明不该改)

1. **SpscRing 满环/空环语义**:Push 的 full 检测 `tail-head==capacity`(spsc_ring.h:99)+ free-running 索引 + relax/acquire/release 组合,经代码推演(dataplane 中 rx/tx 各自唯一生产者、唯一消费者),无 ABA/lost-wakeup(PopBatch 不阻塞,轮询模型无 wake)。**P0 排除**。
2. **跨线程 SpscRing**:推送到 `tx_rings[i]` 的**唯一生产者始终是 worker i**(t_worker_index=i 在 WorkerLoop 入口设置,dataplane.cpp:2900),消费者唯一是 RX/TX loop(dataplane.cpp:2157)。bridge 线程经 mutex 队列→RX loop 转发(OnBridgeFrame → bridge_control_queue_ → DrainBridgeControl),不入 ring。**契约成立**。
3. **neighbors.Consumer/Snapshot 并发**:RCU 快照不可变、引用计数生命周期;控制线程唯一写者。见 D。**成立**。
4. **UdpFlowTable 跨线程迭代器失效**:每 worker 独享 table;UdpRelay::Touch 的单线程内回调(io_context::poll 同一 worker)。Sweep 与 Touch 同线程。dtor 时先断链表(dtor 在 worker 线程 join 之后,udp_tables.clear 在 io_contexts.clear 之前,dataplane.cpp:1424-1425)。**成立**。
5. **IcmpRelay 标签表并发**:TagAllocator 全局单例 + mutex 串行化(Allocate/Consume/Sweep/InFlight/Free 全部加锁);分配唯一写点 HandleIcmp(worker 0 与各 worker 皆调 Instance())。固定 65535 池 + free list(icmp_relay.cpp:14-58)无越界(池大小=65535,初始填 1..65535,count==65535 恰好满)。**成立**。
6. **MacTable LRU/容量淘汰**:`entries_` 扩容只在重哈希时,但 Learn 对已存在 key 的刷新分支(entries_.find)零分配;新 key 在 `entries_.size()<capacity` 时 `operator[]` 可能 rehash → 已包 try/catch(bridge.cpp:207-214);tables 满时走 O(1) 淘汰(bridge.cpp:40-55)。**成立**。
7. **[乙审 B-补充] icmp tag "32-bit/16-bit" 术语误差**:tag 实为 uint16_t(icmp_relay.h:5-6 头注释称 "32-bit tag" 与 :69 `kTagCapacity=65535` 不符)。实际实现自洽(16 位 tag 空间 + 65535 池),**无功能缺陷**,仅 P2 注释术语修正。「GLOBALLY UNIQUE」跨 worker 唯一性由全局单例分配器保证无误。
8. **[乙审 A-交叉确认] rate_limiter/neighbors 的单线程前提**:AllowUplink/AllowDownlink 唯一调用点 = RX/TX loop 线程(dataplane.cpp:2166/2520),SweepIdle 由 Allow 内 piggyback 触发同线程;neighbors.Learn 唯一调用点 = RX loop(dataplane.cpp:2400/2434/2498/2504/2508 等);bridge MacTable 独立互不共享 —— 各表线程隔离无重叠。**成立**。
9. **[乙审 config-交叉确认] ring_capacity≥rx_batch 边界**:config.cpp:1363-1374 已显式拒绝 `rx_batch > ring_capacity`(batch34m),环无法被单次读超量溢出。**成立**。
