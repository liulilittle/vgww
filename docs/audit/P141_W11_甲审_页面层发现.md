## A. [P2·修正] settings.cpp - 保存 Web Token 后 dirty 窗口 + guard 短窗(非永久)

### 修正原因(乙审反证成立)
原判"dirty 永真 / mirror 永 false / ConfirmLeave 恒打扰 / guard 永解除"的四个连锁**不持续**。
关键:settings.cpp:1619 `applied_ = from_snapshot;` **无条件执行**(非仅 mirror 分支)。FromConfig(settings.cpp:205-241)从不读 web_token(token write-only 不进快照)→ from_snapshot.web_token 恒 "" → Save 后首个 Update 即用无 token 基线覆盖 applied_。

### 实际缺陷(窗口形态)
1. Save 成功:settings.cpp:1726 `applied_=draft`(web_token=输入值)→ :1734-1735 清空输入框 → :1737 RefreshDirty 比较 `ReadDraft().web_token=""` vs `applied_.web_token=输入值` → dirty=true、guard 解除(settings.cpp:1469-1471)。
2. **窗口 = [Save 后, 下一个快照 Update]**。worker 完成 → RequestRefreshAfter(0)(snapshot.cpp:335)→ ≤~200ms-1s 后 Update → :1619 覆盖 applied_=from_snapshot(web_token="")→ 下一个 RefreshDirty(settings.cpp:1660)比较 ReadDraft("") == applied_("") → dirty=false、guard 复武装、mirror_snapshot 恢复(自愈)。
3. 窗口内用户双击/连点 Save(apply_live 可能 0.5-2s)→ guard 未复武装 → **重发 SaveConfigCmd、二次重启 data plane、双 toast**;dirty badge 窗口内闪烁(两次 Relayout)。

### 可达性
Settings → 高级 → 输入新 Web token → 保存,在 apply 未完成前再点保存。仅 token 型保存开启该窗口(普通保存 applied_==控件,guard 保持武装,双击被拦)。

### 测试缺口
test_ui.cpp:5717-5898(TestB269)只断言命令 token 载荷,不驱动"保存后立即再次保存"与 dirty_badge 窗口态;:5856-5858 注释承认"token 回空不足以使 draft==applied_",佐证保存点错位存在。

### 最小修复方案
清空输入框同时同步基线:
```
token_input->SetValue(std::wstring());
applied_.web_token.clear();   // 基线匹配可见控件,消窗口
```
或在窗口内禁用 Save 按钮(保存后直到首个新快照)。

## B. [P1] settings.cpp - batch33i 空 adapter 自动选中与保存值脱节(首次运行/空配置直存 Settings 场景)

### 证据
- settings.cpp:1433-1441(空配置 adapter 时 picker 自动选中最可用设备):
  ```
  if (selected.empty() && !choices.empty()) {
      selected = choices.front().value;
  }
  ```
- settings.cpp:1446 `adapter_pick_->SetSelectedValueSilent(selected);` — 只改控件显示。
- settings.cpp:816-821 真正同步 `adapter_value_` 的唯一入口是 picker 的 on_changed:
  ```
  if (!value.empty() && value != L"__none__") { adapter_value_ = value; ... }
  ```
- settings.cpp:1226 `ReadDraft`:`draft.adapter = adapter_value_;`(独立的成员,非 picker 选中值)。
- SelectElement::SetSelectedValueImpl(controls.cpp:3877-3879):`if (value == selected_) return;` — 已经选中的行再次点击也不触发 on_changed。
- 测试 TestB33iEmptyAdapterDefaultsToBest(test_ui.cpp:34418-34473) 只断言 picker 的 selected_value,不断言保存命令的 config.adapter。

### 根因链
首次运行/空配置(config.adapter="")且检测到至少一个 adapter:
1. Update→RefreshAdapterOptions 把 picker 显示自动选为最可用设备(如 "NIC 1"),但 `adapter_value_` 保持空。
2. 用户看到 picker 已选中 NIC 1,点 Save → `draft.adapter = adapter_value_ = ""`。
3. Save 成功(core::ValidateConfig 不校验 adapter 非空,config.cpp:1414 只查长度)→ 保存的 config.adapter=""。
4. 下次数据平面启动时绑定失败;设备表/仪表盘显示没有绑定。

按钮禁用条件 `adapters_empty_ && adapter_value_.empty()`(settings.cpp:1657)在此场景为 false(adapters 非空)→ Save 可用。

### 可达性
首次运行(空配置)时用户可不走向导、直接进 Settings 保存;或配置文件本就没有 adapter 字段。保存结果的破绽要等下次启动才显现 —— 典型的"显示与保存不一致"操作坑。

### 最小修复方案
batch33i 自动选中时同步 `adapter_value_`:
```
if (selected.empty() && !choices.empty()) {
    selected = choices.front().value;
    adapter_value_ = selected;   // 与 picker 显示保持一致
}
```
(需要确认该赋值不应在 `shown` 非空且 `matched` 的分支执行,只在空配置缺省分支。)

## E. [P2] format.cpp - FixedTimeText 超过 99 小时列宽扩展(格式注释与实际不符)

### 证据
- format.cpp:78-86:
  ```
  swprintf(buf, 48, L"%02llu:%02llu:%02llu", hours, ...)
  ```
  `%02` 是最小宽度,超过 99 小时会输出 3+ 位("100:00:00")。
- 注释(format.h:27-29 / format.cpp:76-77)声称 "the shape never changes after a week of uptime" — 事实一周=168h 已超 2 位。
- 测试仅到 90000s=25h(test_ui.cpp:29642-29649)。

### 分析
- 运维长时运行(>99h)或粗粒度 uptime 显示时列宽从 `HH:MM:SS`(8 字符)扩到 `HHH:MM:SS`(9+),表格列宽抖动,视觉 P2。无数据损坏、无越界(48 缓冲远够)。
- **可达成比 uptime 容易**:租约可达 8760h(v4) / 31536000s=8760h(v6)。一个刚签发的一年期 DHCPv6 租约在 leases 页立刻渲染 "8760:00:00"(4 位小时)。所以不是只有"长期运行"才触达,是**大租约即时触达**。
- 测试仅覆盖到 90000s=25h(test_ui.cpp:29642-29649),8760h 场景无覆盖。

最小修复:小时 `%03llu` 不行(1h 变 3 位);可用 `std::min(seconds/3600, 99u)` 上限,或改为 `%04...` 固定 4 位(所有合法租约都 < 10000h,4 位恒定)。需定义产品意图;不改也不构成正确性 BUG。

## H. [P2] dashboard.cpp - uptime 语义与注释不符(进程寿命 vs 服务会话)

### 证据
- controller.cpp:872 `started_(steady_clock::now())`(RealDataSource 构造 = UI 进程启动)。
- controller.cpp:955-958 `uptime_s = published_at - started_`。

### 分析

严重度:语义 P2(注释 + 用户理解)。若要"服务会话 uptime"需在 Start 时重置基准(controller 需订阅命令事件,超出页面层)。**证明不该在此层改;若改需跨层方案。**
