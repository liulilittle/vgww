## 1. V1 裁决：**通过，并撤回我此前的断言(4)**

### 1.1 我此前的断言错在哪里（自我更正）

我上一轮的断言(4)是「DumpLeases 不得覆盖损坏文档」，理由是"原路径应保留副本"。

**该断言错了**：`SetAsideFile` 的语义就是**把原文件移到 `<path>.corrupt`**（`[READ: src/proto/dhcp.cpp:1247-1268]` 的 `corrupt()` 也是同一套），因此原路径在留证后**本就应为空/不存在**。要求"原路径保留副本"与既有 batch82/batch120 契约冲突——那两个 batch 建立的就是"移走 + 标志"。

**结论：撤回断言(4)。留证是否达成的正确判据是「`.corrupt` 副本包含原始字节」，不是「原路径仍是原文」。**

### 2.2 你问的 ①：16384 是否仍能在 2 MiB 文件内被触达

**可达，且余量很大**（`[BASH]` 算术）：
```
v4 最短合法条目 '{"mac":"02:00:00:00:00:00","ip":"10.0.1.1"},' = 44 B
  2 MiB / 44 B = 47662 条  >>  16384  ✓
v6 最短合法条目 '{"duid":"00","iaid":1,"ip":"::1"},' = 34 B
  2 MiB / 34 B = 61680 条  >>  16384  ✓
16384 * 44 = 720896 B = 704 KiB（远低于 2048 KiB）
```
测试本身也证明可达：`[READ: tests/test_dhcp.cpp:1349]` 生成 `limit + extra = 16392` 条，测试能加载并命中 gate（说明文件未超限）。**接受该举证。**

**但注意**：16384 的实际语义是"文件可注入条数上限"，不是"表上限"。当前 `kMaxLeasesBytes`=2 MiB 允许最多 ~47k 条 v4 记录，而 gate 只放行 16384 条 → **剩余 ~31k 条会被静默丢弃**（计 `dropped`）。这与 V6 同源（见 §3），属"文件容量与表容量不协调"，但单独看不构成数据丢失（因为有 `dropped` 计数 + 日志），故不阻断 V2。

### 3.2 **新缺陷 V6（阻断）：大表 dump 出超过 2 MiB 的文件 → 重启即 `kCorrupt` 丢全部租约**

**红线（可执行复现）** `temp/p145_verify/probe_dump_loader_gap.cpp`：
```
clients=27000  serving_cap=262144  file_cap=2097152 bytes
granted=27000 table=27000
dumped bytes=2201720  loader cap=2097152
restart outcome=2 dropped=0 restored=0
CHECK failed: a file this build wrote must restore on the next start
probe_dump_loader_gap: FAIL (1 failures)   EXIT=1
```

`outcome=2` = `kCorrupt`（`[READ: src/proto/dhcp.h:...]` 的 `LoadOutcome` 枚举：0=kRestored/1=kNoFile/2=kCorrupt/3=kUnreadable）。

**根因链（三处常量互不协调）**：
1. **写端无上限**：`DumpLeases` 逐条 `json << row.dump()`（`[READ: src/proto/dhcp.cpp:1143]` 附近）后直接 `WriteFileAtomicDurable`，**不检查总大小**；`[BASH: Select-String 'kMaxLeasesBytes' src/proto/dhcp.cpp]` 只在**读端**出现（`:1352`、`:1402`）。
2. **读端有硬上限**：`[READ: src/proto/dhcp.cpp:1337]` 附近 `if (sz2 > kLeaseCap2) return corrupt();`（v6 `[READ: src/proto/dhcp6.cpp:1186/1228]` 同型）。
3. **V3 把服务上限抬到 262144**（`[READ: src/core/limits.h:56]`），使"表中条目数"首次可以超过"2 MiB 文件能装的条目数"（实测 ~24000 条 v4 即越界，`[BASH: 27000 条 → 2201720 B > 2097152 B]`）。

**后果（P1）**：合法配置（`/16` 池 65534 个可用地址 + 2.4 万以上活跃客户端，**低于** serving cap 262144 也**低于**池规模）→ 60 秒一次的 dump 写出 2.2 MiB 文件 → **下次启动 `kCorrupt` → `SetAsideFile` → 全部租约丢失**。且每次重启复现（因为表又从空开始累积）。

**这是 V3 引入的新可达路径**：V3 之前 `cap=8192`，最多 8192×85 ≈ 696 KiB < 2 MiB，永不触发。**所以 V6 必须随 V3 一起修**。

**最小修复（三选一，推荐 1）**：
1. **写端自限**：`DumpLeases` 序列化后若 `data.size() > kMaxLeasesBytes`，则**不写**（保留上一份好文件）并 `++persist_failures_` + 告警——"永不自伤"的最小改动，且不改变读端契约。
2. 提高 `kMaxLeasesBytes` 使其 ≥ `kMaxLeaseTableHardCap × 最大单条字节`（262144 × ~120 B ≈ 30 MiB）——内存/IO 代价大，需评估。
3. 把 `kMaxLeaseTableHardCap` 降到"2 MiB 能装下的最大值"（~24000）——但这又把服务上限压回了运维可感知的数值，需产品决策。

**红测（须新增）**：填表至 `kMaxLeasesBytes/85 + 1` 条 → `DumpLeases` → 断言 `LoadLeases` 返回 `kRestored` 且条目数不减少（即"写出的文件自己一定读得回来"）。

### 3.3 附带发现 V7（P2，注释/数值不一致）

`[READ: src/core/limits.h:52-55]` 注释写 "far above any legal pool (v4 /16 = 65534 addresses, v6 default pool = 4096)"。

**但 `/8` 也是合法配置**：`[READ: src/core/config.cpp:1181-1186]` 只要求 mask 是"连续 1 前缀"，`/8`（255.0.0.0）通过；`[READ: src/core/config.cpp:1198-1206]` 不限制池规模。`/8` 池 ≈ 1677 万个地址 ≫ 262144。

所以 `kMaxLeaseTableHardCap=262144` **并非** "far above any legal pool"——它会在 `/8` 池的第 262145 个客户端处拒绝服务（并报 `pool_exhausted`）。这是 P2（极端配置 + 需 26 万客户端），但**注释与事实不符**，且与 V3 的立论（"合法池永不触发"）矛盾。

**最小修复**：改注释为真实语义（"防御性硬上限，适用于 ≤/14 的常见池；更大池需同时调整"），或在 `ValidateConfig` 里限制池规模 ≤ 262144（与 V3 的立论对齐）。

## 8. 反思（先于结论）

- **检查项**：V1 留证口径与 `SetAsideFile` 语义对账；V2 gate 位置 + 16384 可达性算术；V3 两处 return + 262144 与池规模关系；第三方断言 `git diff` 删除行核对；三组变异的**独立**重建-运行-恢复循环。
- **偏差（我上一轮的）**：断言(4)「DumpLeases 不得覆盖损坏文档」基于错误前提——我假设证据应留在原路径，但 `SetAsideFile` 的契约就是"移走"。**这是我探针口径错，不是产品缺陷**，本轮已撤回并改用正确判据（`.corrupt` 含原始字节）。教训：**断言必须对齐既有契约的语义，而不是我自己对"留证"的直觉。**
- **偏差（执行方的）**：V3 只对齐了"服务上限"，未同时审计"持久化容量" → 引入 V6（大表写出自读不了的文件）。这与上一轮 V2 的错**同型**：修一个上限时未检查与之耦合的另一个上限。
- **我的变异测试发现**：执行方称"两处同改才红"，我复跑确认属实，但进一步发现**单独改任一处都不红**——说明 262144 的生效路径无测试覆盖（P2 测试缺口）。若只采信"两处同改能红"就盖章，会漏掉这个缺口。
- **教训**：①「能变红」不等于「覆盖了目标分支」——必须逐处变异，等价变异/死代码变异要单独指出；② 任何"提高上限"的修复都必须同时检查**所有与该上限耦合的其他上限**（本轮 8192→262144 与 2 MiB 文件的耦合就是典型）；③ 恢复源码后必须验证**产物真的重建了**（我第一次复跑仍红，是因为 mtime 未更新导致 msbuild 跳过）。
- **W5 未验证**：① V6 的 27000 条场景是 API 级压测，未在真实 WinpkFilter 链路 + 真实 DumpLeases 定时器（60s）下复现；② 全量 49/49 与 hygiene 依赖主代理日志，本轮未独立重跑；③ V7 的 `/8` 池 262145 客户端未实测（仅源码推导）；④ 262144 硬上限的生效路径无测试（V5.2 已说明）。
