## 2. P0 / P1 逐项

### P0：无

从线上可到达的越界读/写、UAF、整数溢出溢出到指针运算：**未发现**。见 §3 覆盖清单与 §4 的"不该改"清单（`MAX_ETHER_FRAME` 前置守卫、classifier 长度不变量、各 builder 的 resize 与源长度）。

### P1-1 DHCPv6（含 v4 同型）租约表无上限 → 远程内存增长 + RX 线程停滞

**症状**
`dhcp6::Dhcp6Server::leases_` 与 `dhcp::DhcpServer::leases_` 都是按"客户端标识 + IAID / MAC"为键的 `unordered_map`，**没有任何条目上限**（`limits.h` 全文 55 行只有文件字节上限 `kMaxLeasesBytes/kMaxLeases6Bytes`，没有条目数上限）。插入点：
- `[READ: src/proto/dhcp6.cpp:564]` `Lease& lease = leases_[key];`（runtime 静态分支）
- `[READ: src/proto/dhcp6.cpp:575]`（config 静态分支）
- `[READ: src/proto/dhcp6.cpp:627]`（请求 IAADDR 命中分支）
- `[READ: src/proto/dhcp6.cpp:686]`（池遍历分配分支）
- v4 同型：`[READ: src/proto/dhcp.cpp:357,368,458,507]`

**根因链（调用方 → 解析器）**
1. `[READ: src/runtime/dataplane.cpp:2772-2786]`：`FrameClass::kDhcpV6` → `ParseDhcp6Frame` 成功后**无条件**调用 `dhcp6_->HandleFrame(...)`。
2. `[READ: src/proto/dhcp6.cpp:160-1630]`：`HandleFrame` 第一步只做 `view.client_duid.empty()` 与 `AllowFrame(view.client_duid, now)`（每题 8 帧/秒）。
3. `[READ: src/proto/dhcp6.cpp:1630-1640]`：`kDhcp6MsgSolicit` 分支**即使没有 IA_NA** 也调用 `Acquire(...)`；`ParseDhcp6Frame` 的 `RequiresIaNa()`（`dhcp6.cpp:73-85`）对 SOLICIT 返回 false，所以最小合法 SOLICIT = 4 字节 msg+xid + option 1（DUID），约 122 字节以太帧。
4. `[READ: src/proto/dhcp6.cpp:559]` `const Key key{duid, iaid};`，`[READ: src/proto/dhcp6.cpp:686-692]` 池遍历命中即插入，**不检查 `leases_.size()`**。
5. 速率限制的键是 DUID 本身：`[READ: src/proto/dhcp6.cpp:731] rate_limit_[DuidKey(duid)]`，且 `[READ: src/proto/dhcp6.cpp:721-726]` 满 4096 条**整体 clear** —— 攻击者用随机 DUID 轮换即可同时绕过"8 帧/秒"与"4096 条"两个约束。
6. 每帧保留成本 ≈ `Key{vector<uint8_t> duid(最长 128B → 堆分配), iaid}` + `Lease{16B ip, string hostname}` + 节点开销 ≈ 250B；入站 122B → **约 2 倍以上**内存放大（DUID 越长放大越大）。
7. 同一个 `Acquire` 在 `mutex_` 内执行（`[READ: src/proto/dhcp6.cpp:545]`），而 `HandleFrame` 由 RX/TX 线程同步调用（`dataplane.cpp:2137 DispatchFrame` 在 `RxTxLoop` 内）——租约表越大，每次分派越慢，转发吞吐随攻击线性下降。

**可达性**
- 前置：`mode=main` 且 `ipv6.dhcpv6.enabled=true`（`dataplane.cpp:1079-1081`）。
- 攻击者：同一 L2 局域网内任意主机，发 UDP 546→547 的 SOLICIT，DUID 每次随机。
- 上限：**只有池大小**。默认池 `prefix::1000-::1fff` = 4096 个 IID（`dhcp6.cpp:496-503`）→ 默认配置下被限制在 4096 条（约 1MB），危害有限；但 `config.cpp:1314-1326` 只要求 `pool_end >= pool_start` 且都在 ULA prefix 内，**允许配置成 `::1 ~ ::ffff:ffff:ffff:ffff`**（/64 部署的常见写法），此时无界。
- v4 同型：池必须落在 LAN 内（`config.cpp:1192-1233`），/8 的 LAN 池 = 1600 万条 ≈ 1.6GB；同样无条目上限。

**严重级判定**
远程可达、无认证、可导致数据面线程长期停滞与内存耗尽；默认配置下被池大小兜住 → **P1**（条件：池规模大于数千地址）。

**建议最小方案**
在 `Acquire` 的插入点前加一个与池无关的硬上限（例如 `limits.h` 新增 `kMaxLeases = 4096`），超限时**优先复用/驱逐已过期条目**，仍满则返回 0（v6 走 NoAddrsAvail，v4 保持静默）。上限必须放在 `mutex_` 内（与插入同锁），且与 `Leases()/DumpLeases()` 的遍历成本一致。注意：`AllowFrame` 的 8/s 不能替代该上限（键可伪造）。

### P1-2 DHCPv6 池遍历的 `ReservedByStatic` 让复杂度回退为 `O(pool × bindings)`

**症状**
`[READ: src/proto/dhcp6.cpp:645-653]` 注释声明"host-set keeps this O(leases + pool_size)"，但循环体内 `[READ: src/proto/dhcp6.cpp:682-684]`：
```
if (0 == index || ~0ULL == index || taken ||
    ReservedByStatic(duid, candidate)) { continue; }
```
`ReservedByStatic`（`[READ: src/proto/dhcp6.cpp:524-538]`）对每个候选做 **config 绑定线性扫 + runtime 绑定线性扫**。

**根因链**
1. `HandleFrame` SOLICIT/REQUEST/RENEW/REBIND 都会进 `Acquire`（`dhcp6.cpp:1632/1652`）。
2. 当池被占满（或候选段都被 `taken/declined/reserved` 跳过）时，`Acquire` 会走完整 `pool_size` 次循环（`dhcp6.cpp:662`），每次一次 `ReservedByStatic`。
3. 绑定上限 `kMaxStaticBindings6 = 1024`（`limits.h:34`）；默认池 4096 → 单帧最坏 **4.2M** 次 16 字节比较，全部在 `mutex_` 内（`dhcp6.cpp:545`），并且 `HandleFrame` 跑在 RX 线程上。
4. 无需占满池也能触发：只要 `taken` 判定不命中（`occupied` 只统计未过期租约），每个候选都会做一次 `ReservedByStatic`；1000+ 条绑定即可把单帧成本放大 1000 倍。

**可达性**：局域网任意主机；需要 `ipv6.dhcpv6.enabled` + ≥ 数十条静态绑定（WebUI 可配，上限 1024）。

**建议最小方案**：在 `Acquire` 开头把 `ReservedByStatic` 的地址集合预构建成 `unordered_set<array<uint8_t,16>>`（config+runtime 一次扫描），循环内改为 O(1) `count()`；与 v4 的 `reserved_hosts` 做法保持一致（`dhcp.cpp:407-418` 已这么做）。同时修正 `dhcp6.cpp:645-653` 的复杂度注释。

## 4. 「证明不该改」清单（附守卫位置/调用方预检/测试契约）

1. **`DispatchFrame` 的 `len > MAX_ETHER_FRAME` 前置守卫不需要放宽或加 jumbo 分支**
   `[READ: src/runtime/dataplane.cpp:2317-2320]`；`MAX_ETHER_FRAME` 来自 `ndisapi/Common.h:96` = 1514，且 `CMakeLists.txt` 全文无 `JUMBO_FRAME_SUPPORTED` 定义（`[BASH: Select-String CMakeLists.txt JUMBO -> 无匹配]`），即 `m_IBuffer` 就是 1514 字节。`AppendDown` 的 1510/1514 上限与之同源。改成 9014 会立刻越界写驱动缓冲。

2. **inbound `kIcmpV4` 分支在 `memcpy(&dst_net, ip+16, 4)` 前没有本地长度检查，不该补"看起来更安全"的重复守卫**
   `[READ: src/runtime/dataplane.cpp:2566-2570]`；`view.cls == kIcmpV4` 只能由 `ClassifyFrame` 置位，而 `ParseIpv4Header` 在 `[READ: src/dsp/classifier.cpp:35-47]` 已保证 `ip_cap >= 20`（`len >= 34`）。补 `if (ip_len >= 20)` 是无害的冗余，但**不能**把它当作"修复"——真正防回归的是 classifier 契约（`tests/test_fuzz_parsers.cpp:213-220` 的后置断言已覆盖）。若未来有人在 `DispatchFrame` 里重排分类顺序，必须同步保这条不变量。

3. **`ParseDhcpFrame` 要求 `udp_len_field == len-14-ihl`（严格相等），不该放宽成 `<=`**
   `[READ: src/proto/dhcp.cpp:86-91]`。合法 DHCP 帧最小 14+20+8+240 = 282 字节 > 以太网 60 字节填充门槛，驱动回报的 `m_Length` 不会含填充；放宽只会让"自报长度"重新成为下游偏移的依据。测试契约：`tests/test_dhcp.cpp:186-210`（ihl/长度错配必须拒）。

4. **`ParseDhcp6Frame` 要求 option 流"恰好消费"（`pos != payload_len` 即拒），不该容忍尾随字节**
   `[READ: src/proto/dhcp6.cpp:229-231]`。RFC 8415 §21.1 规定选项区由选项填满；容忍尾字节会让下游 `iaid/ia_addr` 的取值随垃圾字节漂移。测试契约：`tests/test_dhcp6.cpp:1840-1860`。

5. **`IcmpSegmentLength`（严格）与 `ParseIcmpEcho`（宽）对 `total_len<ihl+8` 的不同处理，不该"统一"**
   `[READ: src/proto/icmp.cpp:36-40]` vs `[READ: src/proto/icmp.cpp:58-60]`。严格版被 `HandleIcmp/HandleIcmpReply/RelayEchoReplyToClient` 用于**决定拷贝长度**（必须拒）；宽版只用于"网关自答"路径，其拷贝上界是 `request_len`（无 OOB）。统一成宽版会把 `HandleIcmp` 的 `seg(icmp, icmp+icmp_len)` 变成按报文自报长度切片。

6. **ARP 被动学习接受 ARP reply（不只 request），不该改成"只学 request"**
   `[READ: src/runtime/dataplane.cpp:2519-2524]`。ARP 本身无认证，限制方向不能阻止投毒，只会丢掉"网关先发 ARP 探测、客户端以 reply 回答"这一必要的学习路径（`ProbeArpFor` 场景）。若要做防护，应是独立的安全特性（静态绑定/DAI），不属于本域最小修复。

7. **DHCPv6 `Acquire` 中 `next_index_ = req_index + 1` 的 64 位回绕不是缺陷**
   `[READ: src/proto/dhcp6.cpp:632]`；`next_index_` 参与 `(next_index_ - pool_start_index_ + offset) % pool_size` 的无符号环运算，回绕后结果仍是合法候选（`uint64_t` 模 2^64 与环语义一致）。不要加"饱和钳制"。

### 8.1 分歧1（甲审 P1-1：租约 JSON 字段类型错误致数据面启动失败）

**① 缺陷成立，严重级应为 P2（甲审定 P1 属高估）。**
- 根因确认（硬证）：`[READ: src/proto/dhcp.cpp:1373-1378]` 的 `for (const auto& item : parsed)` 循环内 `item.value("mac","")` / `item.value("ip","")` **在** `try` **之外**——`[READ: src/proto/dhcp.cpp:1310-1324]`（`json::parse` 的 try）与 `[READ: src/proto/dhcp.cpp:1339-1343]`（`file >> parsed` 的 try）都已结束；`[READ: src/proto/dhcp.cpp:1362]` 只持 `lock_guard`。
- 抛点确认：非对象元素 → `cannot use value() with array` = `type_error 306`（`[READ: build_ci6\_deps\nlohmann_json-src\include\nlohmann\json.hpp:2241]`）；对象内字段类型错 → `type must be string, but is number` = `type_error 302`（`[READ: ...\include\nlohmann\detail\conversions\from_json.hpp:98]`）。v6 同型：`[READ: src/proto/dhcp6.cpp:1162-1168]`、`[READ: src/proto/dhcp6.cpp:1222]`。
- 逃逸链：`LoadLeases` 无 catch → `[READ: src/runtime/dataplane.cpp:1044-1046]`（v4 调用点，位于 `StartAll` 的 try 体内）/`[READ: src/runtime/dataplane.cpp:1083-1085]`（v6）→ `[READ: src/runtime/dataplane.cpp:1191-1212]` catch 转 `"dataplane start failed: " + ex.what()` 且 `dhcp_.reset(); dhcp6_.reset(); running.store(false)`。
- **定级理由（为何 P2 而非 P1）**：触发要求租约文件里出现"语法合法 + `version:1` 信封合法 + 字段类型错"的形状；**产品自身永远写不出这种形状**（见 ②）。唯一来源是本地有写权限的第三方/人工编辑，而同一权限已足以写坏 `config.json`——那条路是 `main` 直接 `return 1`（`[READ: src/core/config.cpp:1776-1784]` 解析失败 → `[READ: src/main.cpp:479-483]` `return 1`），比租约文件更"致命"。故该缺陷不构成独立的 P1 攻击面，属"模块自身契约（租约文件永不应阻塞启动）被破坏 + 可诊断性差"。

**② 实际触发条件：自触发不可能。**
- `DumpLeases` 写出的字段类型是固定的：`[READ: src/proto/dhcp.cpp:1136-1141]` `mac=std::string(mac_text)`（snprintf `%02X`）、`ip=ip_text`（ostringstream 十进制）、`expires_in_s=uint32_t`、`hostname=entry.hostname`；v6 `[READ: src/proto/dhcp6.cpp:942-947]` `duid=FormatDuid`（十六进制串）、`iaid=uint32_t` 等。**没有一条路径会写出数字型 `mac`/`ip`/`duid`，或数组型租约元素。**
- 能触发的只有：(a) 人工编辑租约文件（把 `"hostname":null`、`"mac":123`、元素写成 `[...]`）；(b) 第三方工具重写该文件；(c) 共享同一路径的异构版本以 `version:1` 写出不同字段类型（违反本仓库自己的 schema 定义）。
- 前置进一步收窄：v4 只在 `core::AddressServicesEnabled(config) && config.dhcp.enabled` 时才装配并加载（`[READ: src/runtime/dataplane.cpp:1041-1046]`），v6 需再加 `ipv6.enabled && ipv6.dhcpv6.enabled`（`[READ: src/runtime/dataplane.cpp:1079-1085]`）；bypass 模式完全不会读这份文件。
- 另一条**真实**的可达放大：租约文件路径由 `config_path + ".leases.json"` 固定（`[READ: src/main.cpp:502]`），`DumpLeases` 的写入方是另一份配置共用同一 config 路径的实例 —— 只有两个不同版本的 VGWW 指向同一 `config.json` 时才会互相写出对方不认的 `version:1` 形状；这仍是"同机同权限"，不是远程可达。
- 注意：`expires_in_s` 不会抛——`[READ: src/proto/dhcp.cpp:1417-1422]` 先 `is_number_unsigned()` 再取；`hostname` 缺失不会抛（默认 `""`），但**存在且类型非字符串时会抛**（`[READ: src/proto/dhcp.cpp:1452]`）。真正会抛的是 `mac`/`ip`/`hostname`（v4）、`duid`/`iaid`/`ip`/`hostname`（v6）**存在但类型错**，以及元素本身不是对象。

**③ 后果不是"整机不启动"，而是"数据面降级、进程存活"。** 硬证：
- `[READ: src/main.cpp:606]` `if (!dataplane.Start(error))` → `[READ: src/main.cpp:665-676]` 仅对 `AccessDenied`/`DriverMissing` 两类 driver fault 重试，类型异常的文本不匹配 → `dataplane_failed = true` + stderr `"vgww: dataplane startup failed: ... - continuing in degraded mode"`。
- `[READ: src/main.cpp:1173-1176]` 打印 `"VGWW running in DEGRADED mode (dataplane down)"`；`[READ: src/main.cpp:1203]` 正常 `return 0`；UI/WebUI 照常起来（`[READ: src/main.cpp:1050-1055]` 把错误文本塞进 `ui_flags.dataplane_error`）。
- 但**可诊断性差**：`[READ: src/ui/app.cpp:251-265]` `LocalizeDataplaneError` 对未识别文本统一降级为 `DataplaneErrorGeneric`，操作员看不到"租约文件字段类型错"。且 UI 的设置保存走 Stop→Start（`[READ: src/main.cpp:878-882]`），会再次撞同一文件 → 退出码/状态看起来"保存成功但服务起不来"。
- 最小方案（同意甲修方向）：把循环内的 `item.value(...)` 改成"先 `is_object()` + `contains` + `is_string()` 判定，不合法则 `++dropped; continue`"，与 batch119 的 `dropped_leases_` 计数一致；同时 v6 同步。

### 8.2 分歧2（甲审 P2-6：`kMaxEchoReplyFrameBytes=1514` vs VLAN 下 `AppendDown` 的 1510）——**我漏报，判定成立**

- 我在 §3 分别列了 `icmp.cpp:112-164`（"超 1514 返回 0"）与 `dataplane.cpp:3744-3790`（"1514，VLAN 时 1510"），**但没有把两个上限连起来看**，故未发现该交互。明确承认：**漏报**。
- 判定成立硬证：`[READ: src/proto/icmp.h:33-38]` 声明 `kMaxEchoReplyFrameBytes=1514` 且注释称"matching Dataplane::AppendDown's send cap"（注释里的行号 `dataplane.cpp:3668` 已过期，实际是 3744-3790）；`[READ: src/proto/icmp.cpp:124-128]` 仅在 `total_len > 1514` 时返回 0，恰好 1514 会返回一个 1514 字节帧；`[READ: src/runtime/dataplane.cpp:3751-3757]` VLAN 时 `cap = 1514-4 = 1510`，`len > cap` → `++stats->rx_dropped; return;`。
- 精确影响面（v4，`ihl=20`）：回包长 = 14+20+8+payload，故 payload ∈ {1469,1470,1471,1472} 的 4 档（即 `ping -l 1469..1472`，MTU 满载区间）在 **VLAN 启用**时被静默丢弃；v6 同型：回包 14+40+payload_len，payload_len ∈ {1457..1460}（`[READ: src/runtime/dataplane.cpp:2894-2901]`）。
- 附带发现（同一处，计数说谎）：`[READ: src/runtime/dataplane.cpp:2581-2586]`、`[READ: src/runtime/dataplane.cpp:2452-2457]`、`[READ: src/runtime/dataplane.cpp:2898-2903]` 在 `AppendDown` 返回**之后无条件** `++stats->icmp_replies` —— 帧被丢但仍计"已回复"，`/api/status` 与 UI 的 ICMP 计数与实际发送不符。
  - v6 口径更正：`[READ: src/runtime/dataplane.cpp:2888-2900]` 先判 `14 + 40 + payload_len <= len`（`payload_len` 来自 IPv6 头 `ip6[4..5]`，可被对端声称为 0），所以 v6 只能命中上限触发（超大），**不会**命中 `BuildEchoReplyV6Frame` 的 `payload_len < 4` 下界——那条下界由 `[READ: src/proto/ndp.cpp:289-291]` 在 builder 内兜底。v4 侧则由 `[READ: src/proto/icmp.cpp:27-29]` 的 `ip_len >= header_len + 8` 兜底，同样不会出现负 payload。
  - 因此"VLAN 下静默丢弃"只在 `config.vlan.enabled()`（`[READ: src/core/config.h:125-128]`，`id != 0`）时出现；非 VLAN 部署（`kMaxEchoReplyFrameBytes=1514 = kMaxFrameBytes`）不存在该问题。
- 最小方案：调用方按有效上限（`config.vlan.enabled() ? 1510 : 1514`）先判 `14 + ihl*4 + 8 + echo.payload_len`，超限则计独立计数（如 `icmp_too_big`）并**不**自增 `icmp_replies`；或给 builder 增加 `cap` 参数，两处共用同一个上限来源（消除 `icmp.h` 注释与实际的不一致）。

### 8.3 分歧3（甲审 P2-3：classifier 双向认领 67/68，解析器只认 dport==67）——**认可**

### 9.6 本轮反思（先于结论）

- **检查项**：复核甲审 266 行全部 4 项表态；对其"插入必占池地址"前提做反例搜索（枚举 `leases_` 全部 10 处写点 + Key 结构 + Sweep 条件）；复核 `RunGuarded`/`ControlLoop` 的异常传播；核对 `corrupt()` 的唯一入口。
- **偏差（我的）**：§8 里我把 P1-1 的理由写成"租约表无条目上限"，被甲审的"池约束"反驳后才发现我的原始论证**理由不精确**——真正的漏洞不是"表无上限"，而是"**键含客户端可控的 IAID，而静态分支不占池**"。这是"结论对、论证链错"的典型：若不重构，执行方按"加池大小上限"去修，**修的正好不是漏洞**。
- **偏差（甲审的）**：其"每次插入必先占池地址"忽略了 `UpsertBinding`/静态分支这两条不占池的路由；且其未发现 `expires_in_s` 无上限导致池外条目永久驻留。
- **纠正措施**：9.1 给出两条新论证链（静态×IAID、池外永久条目），并明确"若只加池规模上限，漏洞仍在"；9.5 把修复方案改成"按 duid 去重静态条目 + 载入校验池归属 + `expires_in_s` 上限"三条，而不是"限制 pool_size"。
- **偏差（第二轮，我自己的）**：我最初把静态×IAID 写成"2^32 条 → P1"。定量检验后**自我推翻**：per-DUID 限速 8 帧/秒（`dhcp6.cpp:1599-1601`、`dhcp6.h:355`）+ 1 key/帧（`:194` 覆盖赋值）→ 691200 条/天，按 ~120B/条约 80 MB/天；N=200k 时 occupied 建集约 6 ms/帧，8 fps 仅占 RX 线程 ~5% CPU。**这不是 P1**。若我不做这一步就发出，就是"用未量化的推测拔高级别"——与甲审被反驳的错误同型。
- **教训**：**"表的大小受 X 约束"这类论证必须枚举所有插入路径**；只验证最显眼的那条（池走查）就会漏掉静态分支。**同时，任何"可无限增长"的主张必须带上速率与单位成本**，否则级别无从判定：本轮 2^32 的上界是真实的，但 8/s 的闸门把它压回了 P2。结构性正确 ≠ 可利用性成立。
- **W5 未验证**：9.1 的条目成本 120B 与 30ns/op 均为估算（未实测 `sizeof` 与哈希性能；禁构建）；"43690 条"是 2MiB/48B 的算术估算，实际 DUID 长度 10-14 字节会使记录更大、条目更少；静态绑定的 DUID 是否可被 LAN 侧枚举依赖链路可见性，未实测；均未构造实机压力测试。
