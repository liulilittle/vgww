## 1. V10 修复正确性：**通过**

### 1.1 所有 return 路径都经过折叠

`[READ: src/proto/dhcp6.cpp:584-611]` 共 **3 条** return：
| 行 | 路径 | 是否折叠 |
|---|---|---|
| `:603` `return &leases_.emplace(key, std::move(carried)).first->second;` | 有同 DUID 记录 → 折叠后插入 | **是** |
| `:609` `return nullptr;` | 表满（`EnsureLeaseSlot` 拒绝） | 无需折叠（未插入） |
| `:611` `return &leases_[key];` | **无**任何同 DUID 记录 | 无需折叠（表里本就没有 stray） |

**关键：`exact` 快路径的提前 return 已完全删除**（`[BASH: Select-String 'return &exact->second']` → 0 命中）。原实现 `if (exact != end()) return &exact->second;` 会绕过折叠；现在 `exact` 只用于**给 `carried` 播种**（`:586-590`），然后**继续走 `:591` 的循环**做全表折叠。**这是正确修法。**

### 1.2 carrier 拷贝在 erase 之前（迭代器安全）

- `:588` `carried = exact->second;` —— 拷贝，发生在循环（`:591`）**之前**。
- `:594` `carried = it->second;` —— 拷贝，发生在 `:597 it = leases_.erase(it);` **之前**。
- `:597` erase 之后代码不再解引用 `it`（循环用 `it = erase(it)` 的返回值继续）→ **迭代器安全**。

### 1.3 `std::move(carried)` 之后不再使用

`:603` 之后函数立即 return（`:604` 是 `}` 闭合 `if (found)`，`:605+` 是注释与另一条 return 路径）。`carried` 在 move 后处于有效但未指定状态，**从未再被读取** → **安全**。

### 1.4 `emplace` 后 `&...first->second` 引用有效性

`std::unordered_map::emplace` 返回 `pair<iterator,bool>`；即使触发 rehash，**元素引用与指针仍然有效**（C++ 标准 [unord.req] 保证 rehash 只使 iterator 失效，不使 reference/pointer 失效）。`:603` 取 `&...first->second` 是元素引用 → **安全**。

### 1.5 修复后的行为验证

主代理的红证与我的独立复跑一致：`[case iaid=2] loaded=2 after_acquire=1` → 折叠生效。

## 2. 我上轮「exact 快路径必要且正确」的更正

### 2.1 正确性：我错了

我在终验报告 §2.3 写：「exact 命中时不会清理 stray，属**已知残留**（P3）」。主代理裁决其为**契约违反**，依据是函数自身注释 `[READ: src/proto/dhcp6.cpp:561-565]` 明写 "exactly ONE record may exist per DUID"。

**我接受该裁决，且我的定级错了**：
- 我把它当成"理论上可残留的问题"，但函数的**自声明契约**是"恰好一条"；
- 触发路径不是"伪造输入"——`LoadLeases` 按**地址**去重（`[READ: src/proto/dhcp6.cpp:1299-1300]`、`:1370`），而多 IAID 是 DHCPv6 **合法形态**（我自己在上一轮 §③ 论证过）；
- 所以"载入两个合法记录 + 客户端用其中一个 IAID 请求"是**合法可达路径**，不是脏数据注入。
- **结论：这是 P2 级契约违反，我上轮标 P3 属**低估**。**

### 2.2 必要性：我也错了

我在终验 §2.3 写「常见续租 O(1) 命中，全表扫很贵」。**独立复核后该论证不成立**：

1. **`StaticLeaseFor` 只在静态分支被调用**：`[READ: src/proto/dhcp6.cpp:639-641]`（runtime 命中）、`[READ: src/proto/dhcp6.cpp:657-659]`（config 命中）。**没有配置任何静态绑定的部署，调用 0 次**。
2. **即使有静态绑定，频率也很低**：静态客户端走 SOLICIT→REQUEST→REPLY，之后按 T1/T2 RENEW/REBIND；默认 `lease_seconds=3600`（`[READ: src/core/config.h:64]`）→ RENEW 约每 1800 秒一次。
3. **最坏情况也被限速封顶**：`kMaxFramesPerSecond = 8`（`[READ: src/proto/dhcp6.h:372]`）→ 单 DUID 每秒最多 8 次 O(N) 扫描。
4. **O(N) 的实际成本**：N 默认 4096、硬上限 262144。按每元素 ~30ns（我的估算，未实测）→ N=4096 时 ~0.12ms/次，8 次/秒 = ~1ms/秒；N=262144 时 ~7.9ms/次，8 次/秒 = ~63ms/秒（6.3% CPU，且仅限已配置静态绑定的 DUID）。

**结论：O(N) 扫描在静态路径上完全可接受，快路径没有必要。**

### 2.3 若必须保留快路径，同时满足折叠契约的方案

若将来确需 O(1)，正确做法是**先折叠再快路径**，或**扫一遍计数**：

```cpp
// 方案 A（推荐，最小改动）：一次扫描同时做计数与清理
size_t duid_count = 0;
const Key* survivor = nullptr;   // 不保存 iterator，避免失效
for (auto it = leases_.begin(); it != leases_.end();) {
    if (it->first.duid == key.duid) {
        ++duid_count;
        if (0 == duid_count) carried = it->second;   // 第一条
        if (it->first == key) carried = it->second;  // 调用方自己的记录优先
        it = leases_.erase(it);
    } else { ++it; }
}
// 此时表内已无该 DUID 的任何记录；count==0 表示全新
```
**关键点：快路径只能省掉"扫描"，不能省掉"折叠"**——折叠本身必须遍历全表（因为 stray 可能在任何位置）。所以"快路径 + 折叠"在算法上是矛盾的：**要么扫、要么不折叠**。这就是删除快路径是正确选择的原因。

**方案 B（若真的需要 O(1)）**：维护一个 `unordered_map<duid, Key>` 索引，Acquire 时 O(1) 找到该 DUID 的记录，但仍需遍历确认无 stray——除非同时维护 `duid -> count`。这是复杂度换复杂度的交易，**对静态路径（低频）不值得**。

## 3. MUT-1「等价变异」判定：**不成立（我构造出红证）**

### 3.1 执行方的论证

「`if (!found)` → `if (true)` 不红，因为静态分支无条件覆写 ip/is_static/expires/hostname，carrier 取哪条不可观测。」

### 3.2 该论证的事实错误

**hostname 不是无条件覆写**：
- runtime（WebUI）静态分支 `[READ: src/proto/dhcp6.cpp:648-655]`：
  ```cpp
  lease.ip = runtime->second.ip;
  lease.is_static = true;
  lease.expires = now + term;
  if (!hostname.empty()) {          // ← 条件！
      lease.hostname = reported_name;
  }                                  // ← 没有 else！
  return lease.ip;
  ```
- 当调用方传入**空 hostname**（这是 DHCPv6 线上常态：`[READ: src/proto/dhcp6.cpp:1826-1829]` 的 `Acquire(..., std::string(), requested)`），`lease.hostname` **保持 carrier 带来的值不变**。
- config 分支有 `else`（`[READ: src/proto/dhcp6.cpp:668-672]`）才会覆写，所以配置绑定路径确实不可观测——**但 runtime 路径可观测**。

### 3.3 红证（可执行复现）

探针 `temp/p145_verify/probe_mut1_runtime.cpp`：
1. `UpsertBinding(duid, bound_ip, "")` 建立 **runtime** 绑定；
2. 载入两条同 DUID、不同 IAID、不同 hostname 的记录（`iaid=1/"AAA-first"`、`iaid=2/"BBB-second"`）；
3. `Acquire(duid, iaid=1, ..., hostname="")`（命中第一条 + 空 hostname）；
4. 读 `Leases()[0].hostname`。

**结果（原码）**：`surviving hostname = [AAA-first]` → `probe_mut1_runtime: ALL PASS`（carrier 来自调用方自己的记录）。

**结果（MUT-1：`if (!found)` → `if (true)`）**：
```
surviving hostname = [BBB-second]
CHECK failed: the caller's OWN record must be the carrier
probe_mut1_runtime: FAIL (1 failures)   EXIT=1
```
**改坏 → 红；恢复 → 绿。** 这是**非等价变异**的判决性证据。

### 3.4 额外事实（为什么现有测试没抓到）

我另行验证：把探针改成 `iaid=2`（命中第二条）再跑 MUT-1，结果仍为 `BBB-second`（ALL PASS）——因为**遍历顺序恰好让命中记录最后被覆盖**。这说明该缺陷的表现**依赖遍历顺序**，现有测试（`TestP145B2aExactIaidStillCollapsesStrays` 用 iaid=2）只是**碰巧**掩盖了它。这不是"等价"，是**测试未覆盖该输入组合**。

### 3.5 结论与最小补救

- **执行方的"等价变异"判定错误**，须更正。
- **补一条测试**：runtime 绑定 + 调用方 IAID 命中**非首条**载入记录 + 空 hostname → 断言 `hostname` 为调用方记录的值。
- 定级：**P2**（carrier 优先级契约：调用方自己的记录应优先，否则会把别的 IAID 的 hostname 串到当前 IA 上）。当前实现**正确**（`[READ: src/proto/dhcp6.cpp:586-590]` 的 exact 播种优先于 `:593-596` 的首条），缺陷只在"测试缺失"，不是实现缺陷。
