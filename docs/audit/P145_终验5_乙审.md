## 1. 确定性 MUT-1 杀灭器（本轮核心交付）

### 1.1 为什么前两个方案都不成立

**甲审方案 A**（`P145_W11_终审报告_甲审_第4轮.md` §③）：
```
5) s.Acquire(duid, 9, now, kAck)                 // iaid=9，不匹配任何记录
6) CHECK(s.Leases(now)[0].hostname == "FIRST");  // carrier 取首个匹配
```
**两个缺陷**：
1. `iaid=9` 不命中任何载入记录 → 只测到 `else` 分支（"取首个遇到的"），**完全测不到 `exact` 命中优先**这条真正的契约（`dhcp6.cpp:586-590`）。
2. 它断言"第一个**被迭代**的记录 = 第一个**被插入**的记录"。`std::unordered_map` 的迭代顺序**未指定**（标准 [unord.req]），本例中实测**恰好相反**：载入顺序 iaid=1,2,3,4，迭代出来的首个是 iaid=4。→ **该断言在正确实现上也可能失败，是假红风险**。

**我第 4 轮的单例探针**（`temp/p145_verify/probe_mut1_runtime.cpp`）：
- 只测一个 IAID；MUT-1 下"最后迭代的记录"恰好在某些输入下等于期望值 → 红/绿靠运气。

### 1.2 矩阵探针设计（`temp/p145_verify/r5/probe_mut1_matrix.cpp`）

```
载入 N=4 条同 DUID 记录（iaid=1..4，hostname 各不相同）
对每个 iaid ∈ {1,2,3,4}，在【全新 server】上：
  UpsertBinding(duid, ip, "")     // runtime 分支（hostname 条件覆写，carrier 可观测）
  LoadLeases(path)                // 4 条全载入
  Acquire(duid, iaid, "", kAck)   // 空 hostname
  断言：存活记录的 hostname == 该 iaid 自己的 hostname
```

**顺序无关性证明**：
- 正确实现：`exact` 播种 carrier（`dhcp6.cpp:586-590`）→ **4/4 必过**，与迭代顺序无关。
- MUT-1（`if (!found)` → `if (true)`）：carrier 恒等于"最后迭代到的 DUID 匹配项"，该值对 4 个用例**完全相同** → 最多 **1 个**用例能碰巧通过，其余 **3 个必红**，与迭代顺序无关。

### 1.3 红证实测

**原码（`vgww_core.lib` @ 干净源码）**：
```
iaid=1 own=HOST-iaid1   surviving=[HOST-iaid1] OK
iaid=2 own=HOST-iaid2   surviving=[HOST-iaid2] OK
iaid=3 own=HOST-iaid3   surviving=[HOST-iaid3] OK
iaid=4 own=HOST-iaid4   surviving=[HOST-iaid4] OK
rows pinned to their own record: 4/4
probe_mut1_matrix: ALL PASS (0 failures)   EXIT=0
```

**MUT-1 变体（`temp/p145_mut5/dhcp6_mut.obj` + `/FORCE:MULTIPLE` 独立链接）**：
```
iaid=1 own=HOST-iaid1   surviving=[HOST-iaid4] MISMATCH
iaid=2 own=HOST-iaid2   surviving=[HOST-iaid4] MISMATCH
iaid=3 own=HOST-iaid3   surviving=[HOST-iaid4] MISMATCH
iaid=4 own=HOST-iaid4   surviving=[HOST-iaid4] OK
rows pinned to their own record: 1/4
probe_mut1_matrix: FAIL (4 failures)   EXIT=1
```
**4/4 → 1/4，恰好 1 个碰巧通过，正是设计预期。改坏必红、恢复必绿。**

### 1.4 顺带证实：甲审的 `unordered_map` 顺序假设是错的

`[BASH: diag_keys.exe]` 载入顺序 iaid=1,2,3,4，但 `Leases()` 遍历出的首个是 **iaid=4**（`Leases()` 内部按"静态优先+地址"排序，但 `StaticLeaseFor` 用的是**原始**哈希桶顺序）。MUT-1 下 4 个用例全部得到 `HOST-iaid4`，证明"最后迭代项"是 iaid=4。**甲审若用 iaid=9 断言 `FIRST`（=iaid1），在正确实现上就会假红。**

## 2. 共享工作区污染事件（必须上报）

### 2.1 发生了什么

我在 17:17 首次运行矩阵探针时得到 **原码 1/4 失败**（以为发现新 bug）。排查后确认：

```
[BASH] fc backup5\dhcp6.cpp.bak src\proto\dhcp6.cpp
  550: it = leases_.erase(it);   →  ++it;  // MUT-2      (EnsureLeaseSlot 回收循环)
  597: it = leases_.erase(it);   →  ++it;  // MUT-2      (StaticLeaseFor 折叠循环)  ← 致命
 1675: it = leases_.erase(it);   →  ++it;  // MUT-2      (ReplaceBinding 清理循环)
```
`[BASH] Select-String 'MUT-' src\proto\dhcp6.cpp` → **3 处命中**；`dhcp.cpp`/`limits.h` → 0 处。

即：**有另一个代理在同一工作树上做 MUT-2 变异测试，且未及时恢复**，而我的探针链接的 `vgww_core.lib`（17:17:37 构建）恰好编译自被污染的源码（源码 mtime 17:18:03 才恢复）。

### 2.2 影响与处置

- 我**没有**改动任何产品源码（我的探针只读 `src/proto/dhcp6.h`，变异体在 `temp/`）。
- 我发现污染后：等待所有并行构建/测试结束 → 确认源码哈希回到 `1E180B12...` → 重建 lib（17:19:52）→ 重跑探针 → 4/4 全绿。
- **结论：污染由他人造成，已自愈；但暴露了共享工作区的结构性风险。**

### 2.3 教训

1. **链接型探针无法自证所测代码的版本**。必须在跑探针前**记录并核对** `vgww_core.lib` 的 mtime 与源码哈希，且二者必须一致。
2. 我第 4 轮报告的"原码 AAA-first / 变异 BBB-second"结论**方向正确但证据不可靠**（单例 + 可能测到污染 lib）。本轮矩阵探针已替换它。
3. 建议：变异测试必须在**独立工作树**或按文件复制到 `temp/` 编译（甲审的做法），**禁止直接改 `src/` 再恢复**——恢复失败即污染全组。

## 3. 实现正确性判定：**通过**

`[READ: src/proto/dhcp6.cpp:584-611]`：
- `:584-590` `exact` 命中 → 播种 carrier（`found=true`），**不提前 return**；
- `:591-601` 全表扫描 → 未播种时取首个遇到的（`if (!found)`），**无条件 erase 所有同 DUID 记录**；
- `:602-604` `found` → `emplace(key, std::move(carried))`；
- `:605-611` 全新记录 → `EnsureLeaseSlot` 后 `leases_[key]`。

**4/4 矩阵全绿**证明：`exact` 优先级正确（每个调用方 IAID 都拿到自己的 ip/hostname），折叠幂等（每次都收敛到恰好 1 条）。

### 3.1 但有一个语义待确认（P3，非缺陷）

`Key = {duid, iaid}`（`dhcp6.h:297-303`）→ 不同 IAID 是**不同的表项**。`StaticLeaseFor` 把一个 DUID 的所有 IAID 记录折叠成**一条**，只保留调用方 IAID 的记录。这意味着：**同一台机器如果同时申请两个 IA_NA（两个 IAID），静态绑定下第二个请求会吞掉第一个**——这是 `dhcp6.cpp:561-565` 明写的设计意图（"a static binding is a property of the DUID"），但**未在测试中钉住该行为**。建议补测试明确：静态绑定下多 IAID 客户端只保留最后请求的那条。

## 5. 反思（先于结论，覆盖全程）

### 检查项
1. MUT-1 等价性：构造顺序无关的矩阵探针，原码 4/4、变异 1/4。
2. 甲审方案 A 的正确性：审查其断言前提（`unordered_map` 顺序），用 `diag_keys` 实测反例。
3. 我第 4 轮探针的可靠性：确认其单例设计依赖桶序 → 不合格。
4. 产品实现：逐行审查 `StaticLeaseFor` 的 3 条 return 路径 + 矩阵实测。
5. 环境完整性：发现并处置 `MUT-2` 污染。

### 偏差（我的，必须记录）

1. **我第 4 轮的 MUT-1 红证不可靠**。当时我写"原码 `[AAA-first]` PASS / 变异 `[BBB-second]` FAIL"，并据此声称"判决性证据"。实际上：
   - 单例探针在 MUT-1 下是否红取决于哈希桶序 → 可能碰巧绿；
   - 更严重：那次链接的 lib 可能是**被 MUT-2 污染的构建**（时间窗吻合）。
   → **我上轮把"运气"当成了"证据"。这是方法错误，不是小疏忽。**
2. **我上轮的探针注释与代码不一致**：注释写"Acquire with IAID 2"，代码传的是 `1`；注释还反过来解释"original code → BBB-second"，与代码实际断言 `AAA-first` 矛盾。**说明我当时没有核对探针自身的自洽性。**
3. **本轮一开始我又差点误判**：矩阵探针首次跑出"原码 1/4 失败"，我的第一反应是"发现新 bug"，而非"环境被污染"。**是 `fc` 对比把我拉回来的。** 若我当时直接上报"StaticLeaseFor 有严重 bug"，将是重大误报。

### 纠正措施

- 已将单例探针替换为矩阵探针（4 用例、顺序无关）。
- 已建立"跑探针前核对 `lib` mtime 与源码哈希"的强制步骤（本轮执行：源码 17:18:03 恢复 → lib 17:19:52 重建 → 才跑）。
- 报告中对甲审方案 A 给出**明确不可用**的判定与理由，而非"建议改进"。

### 教训

1. **"改坏红了"不等于"证据成立"**——必须证明**红是必然的**（顺序无关、输入无关）。单例探针在`unordered_map`上永远给不出必然性。
2. **共享工作区的任何测量都必须先验证被测物版本**。`lib` 的 mtime/哈希与源码不一致时，所有结论作废。
3. **变异测试禁止直接改 `src/` 再恢复**——本次污染就是这么来的（不是我，但风险同源）。应复制到 `temp/` 编译。
4. **注释与代码不一致是探针失效的第一步信号**——我上轮就有这个信号却没查。

### 不足 / 未验证（W5）

- 全量 49/49 与 C0 依赖主代理/甲审日志，我未重跑（避免与其并行）。
- `StaticLeaseFor` 的 O(N) 成本我上轮给的是估算（30ns/op），**仍未实测**。
- 静态绑定 + 多 IA_NA 的"第二个请求吞掉第一个"语义，我只做了代码阅读与 4 用例实测，**未核对是否有测试钉住**（建议列为 P146 项）。
- MUT-2 污染者的身份与实际影响范围（是否影响了别人已发布的结论）**我无法判定**。
