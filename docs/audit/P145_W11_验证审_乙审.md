## 1. V2（阻断级）：`LoadLeases` 完全不受新 cap 约束，且与 `EnsureLeaseSlot` 组合导致 DHCP 永久停服

### 1.1 缺陷一：LoadLeases 无任何 cap gate（红证）

`[BASH: git diff src/proto/dhcp.cpp]` 显示 `kMaxDynamicLeases` 只出现在 4 处 `EnsureLeaseSlot` 调用（`:376 :392 :484 :548`）与定义（`:674`）；`LoadLeases` 的插入点 `[READ: src/proto/dhcp.cpp:1527]`（`leases_[mac] = lease;`）与 `[READ: src/proto/dhcp6.cpp:1346]`（`leases_[key] = lease;`）**无任何 gate**。

**可执行红证**（`temp/p145_verify/probe_cap_load.cpp`，链接现成 `build_s4/Release/vgww_core.lib`）：

```
[v4] outcome=0 thrown=0 dropped=69 lease_count=8635 cap=8192
CHECK failed: v4 lease table exceeded kMaxDynamicLeases after LoadLeases
[v6] outcome=0 thrown=0 dropped=0 lease_count=8704 cap=8192
CHECK failed: v6 lease table exceeded kMaxDynamicLeases after LoadLeases
probe_cap_load: FAIL (2 failures)   EXIT=1
```

（`outcome=0` = `kRestored`；文件为 8192+512 条全合法记录，全部通过既有校验。）

### 1.2 缺陷二：超 cap 表 + `EnsureLeaseSlot` = 新客户端永久被拒（红证，功能中断）

`EnsureLeaseSlot` 的放行条件是 `leases_.size() < kMaxDynamicLeases`（`[READ: src/proto/dhcp.cpp:677]`、`:690`；v6 同型 `[READ: src/proto/dhcp6.cpp:543]`、`:553`）。当表因 LoadLeases 已经 **over** cap 时，该条件恒为假，且无过期条目可回收 → **后续每个新客户端都被拒**，直到表自然降回 cap 以下。

**可执行红证**（`temp/p145_verify/probe_dos_after_load.cpp`）：

```
file entries=12288 bytes=1049464 cap=8192
outcome=0 dropped=48 loaded=12240
fresh client got 0x00000000 exhausted_delta=1 table=12240
CHECK failed: Acquire refused a fresh client: the over-cap table (from the file)
permanently blocks EnsureLeaseSlot
probe_dos_after_load: FAIL (1 failures)   EXIT=1
```

即：`kRestored` + `Leases()==12240` + 新客户端 `Acquire` 返回 0 + `PoolExhaustedCount` 递增。

### 1.3 根因链与最小修复

- 根因：cap 只加在**写入路径**（Acquire），未加在**装载路径**（LoadLeases）。
- 因此 cap 不是不变量："表 ≤ 8192" 这个前提被 LoadLeases 破坏后，`EnsureLeaseSlot` 的 `size() < cap` 判定从"还能插入"退化为"永不放行"。
- 最小修复（任选其一，推荐 1）：
  1. **在 LoadLeases 的插入点前复用同一个 gate**（`if (leases_.size() >= kMaxDynamicLeases) { ++dropped; continue; }` 或调用 `EnsureLeaseSlot(now)`），使 cap 成为真正的表不变量；
  2. 或把 `EnsureLeaseSlot` 的判定从 `<` 改为"未超过硬上界时允许挤出"，即超 cap 时先裁剪最旧的过期/最旧条目再放行——但这会让 LoadLeases 的越界状态被"悄悄修正"，语义不如 1 清晰。
- 红测（须新增）：`LoadLeases` 载入 cap+N 条后再 `Acquire` 一个新客户端 → 断言 `LeaseCount() <= cap` **且** `Acquire != 0`；把修复改坏必须转红。

## 2. V3（阻断级）：`kMaxDynamicLeases = 8192` 小于配置层允许的池规模 → 合法配置下 8193 个客户端拿不到地址

### 2.1 事实

- `/16` 池（65534 个可用地址）是配置层接受的合法配置：`[READ: src/core/config.cpp:1198-1232]` 只校验"在 LAN 内 + end≥start + 不含网关/网络/广播"，**不限规模**；`docs/en/configuration.md:85` 也只要求"两端在子网内"。
- cap = 8192 `[READ: src/core/limits.h:36-46]`，其注释自述"twice the default DHCPv6 pool (4096)"，**未与 v4 池规模有任何关系**。

### 2.2 可执行红证（`temp/p145_verify/probe_pool_regression.cpp`）

```
[v4] pool addresses ~ 65534, cap=8192
[v4] granted=8192 table=8192 exhausted=1
CHECK failed: [v4] new client refused while the /16 pool still had free addresses
[v6] granted=8192 table=8192 exhausted=1
CHECK failed: [v6] new client refused while the pool still had free addresses
probe_pool_regression: FAIL (2 failures)   EXIT=1
```

即：**没有任何租约文件**（纯正常客户端），`/16` 池仍有 ~57k 空闲地址，第 8193 个客户端被拒。

### 2.3 判定与最小修复

- 这是**行为回归**而非"新守卫太严"：修复前，`/16` 池可正常服务 65534 个客户端（只是慢）；修复后只能服务 8192 个，且拒绝理由是 `pool_exhausted`（**误导运维**：池并未耗尽）。
- 最小修复（推荐组合）：
  1. cap 改为**与池规模相关**：`min(kMaxLeaseTableHardCap, pool_size)`（v4 用 `pool_size`；v6 用 IID 范围，但 v6 需另设硬上界防巨型池）；
  2. 或保留 8192 但在 `ValidateConfig` 里**同时**限制池规模 ≤ cap，让"配置接受但服务不了"变成"配置直接被拒"；
  3. 无论哪种，`pool_exhausted_` 的语义都需区分"地址耗尽"与"表满"（当前两者共用同一计数与日志，运维无法分辨）。
- 红测（须新增）：`/16` 池 + 8193 个客户端 → 断言全部拿到地址（若选 1）；或断言配置被 `ValidateConfig` 拒绝（若选 2）。

## 4. 逐项复核结果（含我此前的偏差更正）

### 4.1 B2（静态按 DUID 去重）— 通过

`[READ: src/proto/dhcp6.cpp:556-585]` 的 `StaticLeaseFor`：先 `find(key)`，未命中则遍历同 DUID 记录，`erase` 后 `emplace` 到新 key（`:567-577`），仅为**全新 DUID** 才 `EnsureLeaseSlot`（`:581`）。

**引用安全**：`return &leases_.emplace(...).first->second`（`:574`）——`emplace` 返回的 iterator 在 `emplace` 后有效（`unordered_map` 的 rehash 只失效 iterator 不失效引用/指针），且此处立即解引用取地址，**安全**。同理 `return &leases_[key]`（`:584`）也安全。

**是否仍会增长**：同一 DUID 的任意 IAID 序列，第 2 次起走 `:567-577` 的 erase+emplace（净增长 0）；不同 DUID 受 `EnsureLeaseSlot` 限制。**堵住了**。

执行 AI 的 B3 声明（不归零 iaid）我认可：归零会破坏 LEASES 持久化的 IAID 语义（`[READ: src/proto/dhcp6.cpp:944]` 持久化 `entry.iaid`，重载后 key 必须能重建）。

### 4.2 B3（ReservedByStatic 预构集合）— 通过

`[READ: src/proto/dhcp6.cpp:750-764]` 预构 `reserved` 集合（config + runtime 各扫一次），循环内改 `0 != reserved.count(index)`（`:786`）。**注意**：预构时排除了 `binding.duid == duid` 的自己（`:756`、`:761`），与原 `ReservedByStatic` 的 `binding.duid != duid` 语义（原 `:528`、`:533`）**完全一致**——这点执行方做对了，没引入语义漂移。

### 4.3 D（ICMP 上限对账）— 通过

- `DownFrameCap()` = `vlan.enabled() ? 1514-4 : 1514`（`[READ: src/runtime/dataplane.cpp:3802-3807]`），与 `AppendDown` 的实际 cap（`:3755-3758`）**同一算式**——但注意这是**两处独立常量**，若将来改一处会漂移（见 V4 建议）。
- `EchoReplyFits` 是 `icmp_too_big` 的**唯一**自增点（`[BASH: Select-String 'icmp_too_big' src/**]` 仅 `dataplane.cpp:3815` 一处自增）。
- 3 处 ICMP echo 出口全部预算：`:2453`、`:2582`、`:2902`；`icmp_replies` 移入 `if (reply_len > 0 && EchoReplyFits(...))` 内（`:2455-2456`、`:2584-2585`、`:2903-2905`）。
- **第四出口检查**：`HandleIcmpReply`（relay 回程，`:3131-3141`）推 `tx_rings` 而非 `AppendDown`，**未做 cap 预算**——但该路径的帧长来自远端回包且 `BuildRelayedEchoReplyFrame`（`[READ: src/proto/icmp.cpp:166-176]`）无 1514 上限。这是**既有问题**（非本次引入），且 `icmp_replies` 不在此路径自增，故不影响 D 项的"计数真实"目标。归入 V4。

### 4.4 E（expires_in_s 上限）— 通过

`[READ: src/proto/dhcp.cpp:1487-1495]`、`[READ: src/proto/dhcp6.cpp:1299-1306]` 均 clamp 到 `lease_seconds`。探针（`probe_cap_load` 中的 v6 clamp 部分）与仓库测试 `[READ: tests/test_dhcp6.cpp:3082+]` 一致。

**未加 IP∈池校验**（执行方依裁决）：我确认这符合 v4 既有契约注释 `[READ: src/proto/dhcp.cpp:1403-1409]`（"Strict pool-range membership is intentionally NOT checked so a legitimately persisted lease survives a pool re-range"）与 pin 测试 `[READ: tests/test_dhcp6.cpp:1262-1274]`。

**因此我的 C 项残余风险仍在**：文件可注入池外条目（`InPrefix` 通过但不在 `[pool_start,pool_end]`），它们永不参与池复用，只长期占用表槽位（现受 cap 限制，但见 V2——LoadLeases 不吃 cap，故该风险未被抑制）。**残余风险 P2**，与 V2 同源，修好 V2 后自动收敛。

### 4.5 F（option 12 码点回退）— 通过

`[READ: src/proto/dhcp.cpp:189-206]`。探针 `probe_option12`（修正探针自身两处缺陷后）：

```
[a well-formed ] emitted=252 valid_utf8=1
[b ill-formed  ] emitted=251 valid_utf8=1
probe_option12: ALL PASS (0 failures)   EXIT=0
```

- (a) 84×3 字节 + 1×4 字节（256 B）→ 输出 252 B 且 `IsValidUtf8==true`，**未过度裁剪**（保留了 84 个完整码点）。
- (b) 252 个 ASCII + 4 个裸 continuation 字节 → 输出 251 B 且合法。**注意**：`SequenceLength(bytes, size, 252)` 对 `0x80` 返回 0，循环 `--limit` 到 251 时 `bytes[251]='A'`（ASCIID）→ 返回 1 → 停止。因此输出 251 而非 252（少 1 字节），**这是正确行为**：`limit=252` 处是非法字节，必须回退。
- 过度裁剪排查：最坏情况回退 ≤3 字节（UTF-8 最长 4 字节序列），不会出现"截断后远小于 253"。**通过**。
- **fuzz 未覆盖**：`[BASH: Select-String 'hostname|0x0C' tests/test_fuzz_parsers.cpp]` 零命中 → F 项无 fuzz 语料（W5，见 §9）。

### 4.6 关于甲审的「B2 引用安全」质疑

我独立复核：`std::unordered_map::emplace` 返回 `pair<iterator,bool>`；rehash 使 iterator 失效但**不使引用/指针失效**（C++ 标准容器要求）；且 `&...first->second` 立即取址、后续不再解引用旧 iterator。**安全**。

## 8. 反思（先于结论）

- **检查项**：A/B1/B2/B3/D/E/F 七项逐一复核；cap 的全部插入路径枚举（v4 4 处 + v6 3 处 + 2 条 LoadLeases 路径）；ICMP 全部 4 个回包出口；hygiene/ctest/EOL/C0/变异残留独立复跑。
- **偏差（执行方的）**：① cap 只加在 Acquire 路径，LoadLeases 漏掉 → V2；② cap 数值（8192）与配置层允许的池规模（65534）脱钩 → V3；③ A 项拆开后，"部分损坏"落入"不隔离不留证"的中间态 → V1；④ 首版 v4 static 变异两次仍绿却未在摘要中显式登记 → 过程瑕疵。
- **偏差（我的，必须记录）**：第一次 v6 边界探针用了**早于 lib 构建**的 exe（14:17:59 < 14:18:59），得出了"v6 gate 未生效"的**错误结论**；若不复查时间戳就会误报阻断缺陷。**这与我此前批评甲审的"未量化就拔高级别"是同一类错误：未证明工具自身有效性就下结论。** 已纠正（重建后 v6 gate 正常）。
- **纠正措施**：V2/V3 给出可执行红证（两个探针 + 打印出真实数值），而非仅代码索引；V1 给出 4 项断言的红证；F 项的探针先修正两处自身缺陷（offset 推定、断言过严）再判定通过。
- **教训**：① **新增上限必须同时覆盖装载路径**，否则上限就不是不变量，而"上限 + 依赖该上限的 gate"的组合会把越界状态转换成**永久拒绝**——比没有上限更糟。② **新常量的数值必须有配置层的对应约束**，否则"配置接受但运行时服务不了"，且错误码（`pool_exhausted`）会误导运维。③ 验证探针必须**先自证有效**（well-formed 正控制 + 产物时间戳），否则会把工具缺陷当产品缺陷。
- **W5 未验证**：① `probe_dos_after_load` 的 12240 条为探针构造，真实 2 MiB 文件可载入约 24k 条（按 85.7 B/条实测比估算）——该数字未做端到端（含真实 DUID 长度）验证；② V3 的 `/16` 场景是 API 级压测，未在真实 WinpkFilter 链路上验证 8193 个客户端的实际表现；③ F 项的 fuzz 覆盖缺失（`test_fuzz_parsers` 不含 hostname 语料）；④ V1 的"下次 Dump 静默重写"已在探针中复现，但未验证"若 `AtomicWriteDurable` 失败"的分支影响。
