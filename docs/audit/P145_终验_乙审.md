## 2. B2-a 终验：**通过**

### 2.1 全表扫描确实清掉所有同 DUID 记录

`[READ: src/proto/dhcp6.cpp:578-593]`：
```cpp
Lease carried{};
bool found = false;
for (auto it = leases_.begin(); it != leases_.end();) {
    if (it->first.duid == key.duid) {
        if (!found) { carried = it->second; found = true; }   // 只留第一条
        it = leases_.erase(it);                               // 其余全删
    } else { ++it; }
}
if (found) return &leases_.emplace(key, std::move(carried)).first->second;
```
- 循环**不 break**：遍历到 `end()`，所有同 DUID 记录都被 `erase`。
- `found` 保证只 carry 第一条（不是最后一条），语义稳定。
- 变异验证（§7）：把 `erase(it)` 之后加 `break`（回到"只删第一条"）→ `[BASH]` `test_dhcp6.cpp:3226 1 == server.LeaseCount()` + `:3230 1 == leases.size()` → **2 FAILURES**。**这是真测试**。

### 2.2 `carried` 的 move 语义安全性

`[READ: src/proto/dhcp6.h:144-150]` 的 `Lease`：
```cpp
struct Lease {
    std::array<uint8_t, 16> ip{};
    uint32_t iaid = 0;
    std::chrono::steady_clock::time_point expires;
    bool is_static = false;
    std::string hostname;      // 唯一非平凡成员
};
```
- **不含 `std::vector`**（我核对 `[BASH: Select-String 'struct Lease' -Context 0,12 | 'vector|string|array']` → 仅 `array`/`string`）。
- `carried = it->second`（`:583`）是**拷贝赋值**；`it = leases_.erase(it)`（`:586`）销毁原节点后 `carried` 已是独立副本 → **安全**。
- `leases_.emplace(key, std::move(carried))`（`:592`）：move 后 `carried` 处于合法但未指定状态，**但此后不再使用**（立即 `return`）→ **安全**。
- 引用有效性：`emplace` 返回的 iterator 在 rehash 后可能失效，但 `&...first->second` 取的是**元素引用**（unordered_map 的引用在 rehash 后仍有效，C++ 标准保证）→ **安全**。

### 2.3 `exact` 快路径是否仍有必要且正确

`[READ: src/proto/dhcp6.cpp:566-569]`：
```cpp
const auto exact = leases_.find(key);
if (exact != leases_.end()) return &exact->second;
```
- **必要**：常见情形（同一 IAID 反复续租）O(1) 命中，避免每次 O(N) 全表扫。v6 池默认 4096、上限 262144，全表扫在高负载下昂贵。
- **正确**：`find` 命中说明 `{duid, iaid}` 完全一致，此时"每 DUID 一条"的不变量**已满足**，无需清理（若存在其他同 DUID 记录，那只可能是载入器注入的脏数据——但那种情况 `exact` 命中时不会清理，属**已知残留**）。
- **残留风险**：若表中同时存在 `{duid, iaid=1}`（exact）与 `{duid, iaid=2}`（stray），`exact` 快路径命中时**不会**清理 stray。但该 stray 会在下次不同 IAID 的 `Acquire` 时被 `StaticLeaseFor` 清掉，且 `Sweep` 对 static 不清（stray 若也是 static）。**这是 P3 级理论残留**（需要"先注入脏数据 + 客户端只用原 IAID"才触发），归入 V10。

### 2.4 你问的 ③「B2-b 关闭是否合理」——**合理，我独立认可**

执行 AI 的论证链（我逐条核实）：
1. **v6 key 是 `{duid, iaid}`**：`[READ: src/proto/dhcp6.h:297-303]`（`struct Key { std::vector<uint8_t> duid; uint32_t iaid; }`）。
2. **多 IA 是 DHCPv6 合法形态**：RFC 8415 允许一个客户端用多个 IA_NA（每个有独立 IAID）。代码按 `{duid,iaid}` 建键正是为此。
3. **`DumpLeases` 会写出全部记录**：`[READ: src/proto/dhcp6.cpp:1046]` `entry.iaid = pair.first.iaid`（`:1465` 同型），`[READ: src/proto/dhcp6.cpp:1070]` `{"iaid", entry.iaid}` → 每条记录**保留自己的 IAID**。
4. **载入器按地址去重、不按 DUID**：`[READ: src/proto/dhcp6.cpp:1299-1300]` `claimed_ips`，`[READ: src/proto/dhcp6.cpp:1370]` `claimed_ips.insert(tail)`。**不是** `claimed_duids`（`[BASH]` 全仓无此符号）。
5. **若加 DUID 去重 → 自写自读不变量破裂**：自己 dump 的 `{duid, iaid=1}` + `{duid, iaid=2}` → 载入器只留第一条 → 重启丢一半租约。这与 V6 的"写出的文件自己一定能读回"直接冲突。
6. **反向守护测试存在**：`[READ: tests/test_dhcp6.cpp:3155-3184]` `TestP145B2MultiIaidRecordsSurviveLoad` 断言 `2 == server.LeaseCount()` + `0 == dropped`。

**判定：B2-b 关闭正确。** 若要做"载入器 DUID 去重"，唯一不丢数据的形式是"每 DUID 保留**全部** IAID"，但那等于不去重，与目的矛盾。**我无更优方案。**

## 3. 连带影响（B81 夹具 2048→250）：**可接受，非掩盖问题**

### 3.1 事实与定量

`[BASH: git diff tests/test_dhcp6.cpp]` 唯一的行为性改动：`- const std::string filler(2048, 'h');` → `+ const std::string filler(250, 'h');`

规模核算（`[BASH]` 算术）：
```
250B hostname row  = 380 B  → 4096 rows = 1520 KiB  (< 2048 KiB cap)  ✓ 会被接受
2048B hostname row = 2178 B → 4096 rows = 8712 KiB  (> 2048 KiB cap)  ✗ 会被 V6 拒绝
```

### 3.2 判定依据

- **该测试的目的**（`[READ: tests/test_dhcp6.cpp:2088+]`）：验证"dump 期间锁持有时间是 dump 总时长的小比例"（`[READ: tests/test_dhcp6.cpp:2180-2204]` 的 rate ratio 断言）。
- **它需要 dump 成功**：`[READ: tests/test_dhcp6.cpp:2160-2162]` `if (!server.DumpLeases(path, now)) all_dumped = false;`，随后 `[READ: tests/test_dhcp6.cpp:2177]` `CHECK(all_dumped)`。
- **若保留 2048B**：V6 会**正当拒绝**（8712 KiB > 2 MiB），`all_dumped=false` → 测试失败。**这是 V6 的正确行为，不是要测的失败。**
- **250B 仍足够**：1520 KiB 的 dump 包含 4096 条 × 250 字节 hostname 的 JSON 转义与序列化，**序列化工作量与原设计同量级**（原 2048B 也是 4096 条，只是每条更长）；锁竞争的时间结构不变。
- **关键断言未被削弱**：`[READ: tests/test_dhcp6.cpp:2178-2179]` `baseline_probes > 10` / `dump_probes > 10`、rate ratio 断言均在，未删除、未放宽。

**判定：这是对 V6 语义的正确适配（"dump 必须被接受才能测 I/O 行为"），不是掩盖问题。** 唯一的代价是 dump 总字节数从 ~8.7 MiB 降到 ~1.5 MiB，略降低 I/O 占比——但该测试比较的是**同一次调用的锁持有 vs 总时长**（scale-free），绝对值不影响判据。

**W5**：我未做"250B vs 2048B 下 ratio 数值对比"的实测（若 ratio 从 0.03 变 0.05 仍在阈值内，但趋势会变）。若要严格，可加注释记录该权衡——当前 `[READ: tests/test_dhcp6.cpp:2092-2097]` 已有注释说明"4096 rows must also stay under kMaxLeasesBytes so the dump is ACCEPTED here (P145-V6 refuses an unreadable document by design)"，**已记录**。

## 5. V8（P3，我新发现）：v6 写端用了 v4 的常量

**事实**：
- v6 **写端**：`[READ: src/proto/dhcp6.cpp:1094]` `if (data.size() > ::vgww::core::limits::kMaxLeasesBytes)` —— **v4 的常量**。
- v6 **读端**：`[READ: src/proto/dhcp6.cpp:1214]` 与 `:1256` 用 `kMaxLeases6Bytes` —— **v6 的常量**。

**两常量当前等值**（`[READ: src/core/limits.h:16]` `kMaxLeasesBytes = 2*1024*1024`；`:33` `kMaxLeases6Bytes = 2*1024*1024`），故**当前行为等价，无缺陷**。

**风险**：若将来只调整其中一个（例如把 v6 上限提高到 4 MiB），写端仍按 2 MiB 拒绝 → v6 会在 2 MiB 就停止持久化，而读端能读 4 MiB → **写端比读端更保守**（安全方向，不会自伤），但会造成"表很大时 v6 永远存不下"的隐性功能损失，且与"单源常量"的纪律冲突（`[READ: src/core/limits.h:34-35]` 注释自称 "single-sourced"）。

**最小修复**：`dhcp6.cpp:1094` 与 `:1101` 改用 `kMaxLeases6Bytes`。
